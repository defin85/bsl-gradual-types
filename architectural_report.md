Отчет об архитектурном техническом долге (актуализация)

Дата актуализации: 2026-01-31

Цель документа: зафиксировать текущие (на дату выше) архитектурные долги/риски и дать практичные рекомендации.
Документ намеренно фокусируется на «почему болит» и «что делать», а не на полном описании архитектуры.

Контекст (срез текущего состояния)

- В workspace присутствуют отдельные крейты для типов и репозитория: `bsl-types`, `bsl-repository`.
- `bsl-analysis-v2` используется в backend для LSP/семантики (v2 pipeline).
- Flow-sensitive инфраструктура существует, но находится в переходном состоянии:
  - В `bsl-shared` есть flow-sensitive доменная модель и контекст: `shared/src/domain/flow_analysis.rs`.
  - В `bsl-shared` есть CFG в IR: `shared/src/ir/cfg.rs`.
  - В `analysis-v2` построение CFG пока заглушено: `analysis-v2/src/ast_to_ir/converter.rs` (метод `build_cfg()` возвращает `None`).
  - В `bsl-runtime` есть экспериментальные анализаторы потока: `bsl-runtime/src/domain/flow_analyzer.rs` и `bsl-runtime/src/domain/flow_analyzer_simple.rs`, при этом «полный» analyzer не подключен модулем (`bsl-runtime/src/domain/mod.rs`).

1) Flow-sensitive анализ и CFG: раздвоение и незавершенная интеграция
Критичность: Высокая

Описание:

- Существует как минимум два разных типа CFG с одинаковым именем `ControlFlowGraph`:
  - IR CFG: `shared/src/ir/cfg.rs` (используется IR-слоем, в т.ч. `shared/src/ir/program.rs`).
  - Domain CFG: `shared/src/domain/flow_analysis.rs` (используется flow-sensitive доменной логикой, тестами интеграции narrowing/null-safety и экспериментальным runtime analyzer).
- `bsl-analysis-v2` строит IR (через `AstToIrConverter`), но CFG для flow-sensitive анализа пока не формируется (возвращается `None`), из-за чего часть flow-sensitive фич остается вне v2 пайплайна.
- Экспериментальный `bsl-runtime/src/domain/flow_analyzer.rs` содержит TODO по интеграции с `TypeMetadataLookup`, но сам модуль сейчас не является активной частью runtime (не экспортируется из `bsl-runtime/src/domain/mod.rs`).

Риски:

- Путаница типов и границ слоев (IR vs Domain) из-за одинаковых имен и параллельных реализаций.
- Сложность доведения flow-sensitive анализа до production (из-за отсутствия единого «канонического» CFG).
- Потенциальные регрессии при попытке «склеить» компоненты, потому что разные части системы ожидают разные структуры CFG.

Рекомендация:

- Определить один канонический формат CFG и один путь интеграции в v2:
  - либо CFG является частью IR (`bsl-shared::ir`) и используется downstream-логикой;
  - либо CFG является доменной моделью (`bsl-shared::domain`) и строится в рамках доменного пайплайна.
- После выбора:
  - убрать дублирование типов (переименование/удаление второго `ControlFlowGraph` или четкое разведение имен, например `IrControlFlowGraph` vs `DomainControlFlowGraph`);
  - реализовать реальное построение CFG в `analysis-v2` (вместо `None`);
  - либо подключить `bsl-runtime` flow analyzer (если он нужен), либо переместить/удалить как мертвый код.

2) `bsl-shared` как агрегатор слоев: долг уменьшен, но риск «god-crate» остается
Критичность: Средняя

Что уже улучшено относительно прошлой версии отчета:

- Ранее тяжелые компоненты вынесены в отдельные крейты, а в `shared` остались shim/реэкспорт:
  - `shared/src/domain/repository.rs` (реэкспорт из `bsl-repository`);
  - `shared/src/domain/facet_utils.rs` (реэкспорт из `bsl-types`).

Что остается потенциальным долгом:

- `shared` продолжает агрегировать Domain + IR + utils в одном крейте, что увеличивает радиус пересборки.
- В `shared/src/domain` остаются крупные модули (например, `metadata_lookup/*`), и они широко используются.

Рекомендация:

- Если цель — ускорение компиляции/изоляция изменений, рассмотреть следующий шаг:
  - выделить IR в отдельный крейт (условный `bsl-ir`) и ограничить зависимости по слоям;
  - удерживать `bsl-shared` как thin facade (реэкспортный слой) либо постепенно отказываться от него там, где это оправдано.

3) Deprecated/legacy API в `shared/src/engine.rs`: «заглушка ради совместимости»
Критичность: Низкая

Описание:

- В `shared/src/engine.rs` присутствует `AnalysisEngine::new_with_init()` помеченный `#[deprecated]` и содержащий stub-реализацию.
- На текущий момент нет явных consumer’ов этого API (по репозиторию встречается только определение).

Рекомендация:

- Удалить deprecated API (или вынести за feature-flag), если внешних пользователей нет.
- Если нужен для совместимости, явно задокументировать срок/условия удаления и покрыть contract-тестом (чтобы не «случайно» начать использовать снова).

4) Суффикс `-v2` в `analysis-v2`: долг по именованию и восприятию
Критичность: Низкая

Описание:

- `bsl-analysis-v2` де-факто является основным аналитическим движком, при этом суффикс `v2` начинает восприниматься как постоянный.

Рекомендация:

- Запланировать переименование `analysis-v2` -> `bsl-analysis` после стабилизации публичного API.
- Если переименование откладывается, держать четкий документ «почему v2» и что считается критерием окончания миграции.

5) Документационный дрейф (ошибочные пути/модули) как источник архитектурного долга
Критичность: Средняя

Описание:

- Документы могут ссылаться на несуществующие модули/пути и тем самым вводить в заблуждение разработчиков.
  Например, в `backend/src/README.md` описан `domain/flow_analyzer.rs`, но директории `backend/src/domain/` в текущей структуре нет.

Рекомендация:

- Добавить легковесную проверку документации (скрипт/CI job), которая валидирует существование упомянутых путей для ключевых архитектурных документов.
- При крупных миграциях обновлять в одном PR: код + docs + отчеты о долге.

Закрытые/исправленные пункты (для истории)

- «Зависимости агента от application crate»: на текущий момент `bsl-agent` не зависит от `bsl-backend` (зависит только от библиотечных крейтов, включая `bsl-analysis-v2` и `bsl-runtime`).
