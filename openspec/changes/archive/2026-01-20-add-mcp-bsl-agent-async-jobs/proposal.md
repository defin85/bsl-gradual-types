# Change: Асинхронный `bsl-agent` с прогрессом и persist/resume

## Почему
Текущий MCP‑сервер `bsl-agent` выполняет тяжёлую инициализацию и часть семантических запросов синхронно в рамках одного `tools/call`. Это приводит к “подвисаниям” LLM‑клиентов и таймаутам (клиенты MCP часто ожидают быстрый ответ от tools), а также не даёт LLM чёткого сигнала, когда можно запрашивать результат.

Кроме того, при перезапуске Codex CLI (и, соответственно, MCP‑процесса) теряется in‑memory состояние сессии, из‑за чего невозможно безопасно “продолжить” работу без повторных действий.

## Что меняется
- Вводится **job‑модель**: все тяжёлые операции (`startup` и все `bsl_*` семантические tools) выполняются асинхронно как job’ы.
- `workspace_open` становится быстрым и возвращает `startup_job_id`, а прогресс и готовность отслеживаются через `workspace_status`/`job_status`.
- Добавляется **persist/resume** состояния сессий и job’ов на диск, чтобы после рестарта MCP‑процесса клиент мог восстановиться (`workspace_resume`) и переиспользовать результаты/кэши.
- Текущие sync tools `bsl_*` заменяются на `bsl_*_start` (breaking change) + универсальные `job_*` tools для статуса/ожидания/результата.

## Вне скоупа
- Server‑initiated streaming/notifications (push) — прогресс реализуется через polling (`workspace_status`/`job_status`/`job_wait`).
- Чекпоинтинг “продолжения” именно running‑job после рестарта: незавершённые job’ы помечаются как прерванные и должны быть перезапущены.
- Изменение контракта `platform_docs_archive` (файл vs директория) — остаётся как в текущей спецификации.

## Влияние
- **BREAKING:** меняется MCP API: семантические tools становятся асинхронными (`*_start`) и требуют job polling.
- Спека: затрагивается capability `mcp-bsl-agent`.
- Код: `bsl-agent` (session manager + tools), интеграционные тесты MCP, документация по API (если есть).
