# Design: Syntax error enhancers (rewrite/add) поверх tree-sitter ParseError

## Context (current behavior)
Синтаксические ошибки извлекаются из дерева tree-sitter как `ERROR` узлы и `node.is_missing()`:
`syntax/src/tree_sitter_adapter/syntax_errors.rs`.

Сейчас:
- сообщение формируется как `Синтаксическая ошибка: неожиданный текст '...';`
- span берётся из `node.start_byte..node.end_byte`.

Это даёт корректный “syntax is broken” сигнал, но часто плохой UX:
- span попадает в токен “где упало”, а не в первопричину;
- сообщение не помогает понять *какую именно* конструкцию пользователь написал неверно.

## Goals
- Улучшить message/span для распознаваемых паттернов ошибок, не меняя грамматику.
- Работать только при наличии синтаксических ошибок (чтобы не ловить валидный код и не создавать FP).
- Детерминированность: стабильный порядок и контент diagnostics.
- Минимальная стоимость: правила анализируют небольшой локальный контекст (обычно строка/окно вокруг span).
- Политика вывода: в IDE SHOULD быть **не более одной** синтаксической ошибки на строку (rewrite-only, без “спама”).

## Non-Goals
- Полный “второй парсер” или полный репорт “expected tokens”.
- Авто-фиксы/CodeActions.

## Proposed Architecture
### 1) Pipeline
В `TreeSitterAdapter::convert_tree` (см. `syntax/src/tree_sitter_adapter/mod.rs`) после `collect_syntax_errors_cached`:
1. Если `syntax_errors` пуст — не запускать enhancers.
2. Иначе прогнать `enhance_syntax_errors(...)`:
   - на вход: `source`, `LineIndex`, `root_node` (опционально), исходные `Vec<ParseError>`.
   - на выход: новый `Vec<ParseError>`.

### 2) Rule Model
Два типа правил:
- **Rewrite rule**: ищет “сырой” `ParseError` (или набор ошибок) и заменяет его на более полезный:
  - более точный span (например, на ключевое слово `Шаг`);
  - более конкретный `ErrorType` (например, `InvalidSyntax`);
  - более полезное сообщение.
- **Add rule**: добавляет дополнительную диагностику (обычно `InvalidSyntax`/`UnexpectedToken`) без удаления исходной.

В рамках этого change применяется политика **rewrite-only**: правила либо переписывают существующую ошибку,
либо (если не распознали паттерн) оставляют исходную. Add-правила не внедряются, чтобы обеспечить
“не более 1 ошибки на строку”.

### 3) Дедуп и приоритизация
Чтобы избежать “двух ошибок на одну строку”:
- применять “line-cap” после rewrite:
  - сгруппировать ошибки по строке (по `span.start` через `LineIndex`);
  - выбрать 1 ошибку на строку по приоритету:
    1) переписанные `InvalidSyntax` (наиболее конкретные),
    2) `MissingToken` (блоки/окончания),
    3) прочие `ParseError`.
  - tie-breaker: меньший span (уже), затем `span.start`, затем `(error_type, message)` для детерминизма.

Детерминизм:
- сортировать/группировать ошибки по `span.start`, затем по `(error_type, message)` как tie-breaker.

## Initial Rules
### Rule A (narrow, rewrite): `Для ... По ... Шаг ... Цикл`
Условия (примерно):
- на строке есть `ParseError`;
- строка содержит `Для`/`for` и `По`/`to` и `Цикл`/`do`;
- между “`По <expr>`” и `Цикл` встречается слово `Шаг`/`step` и после него есть выражение.

Вывод:
- `ErrorType::InvalidSyntax`
- span на токен `Шаг`/`step`
- сообщение: “В цикле `Для` нет синтаксиса `Шаг <expr>`. Для обратного обхода используйте `Для i = ... По 0 Цикл`.”

### Rule B (general): “unexpected clause in `Для` header”
Если заголовок `Для ... По ...` содержит дополнительные токены/ключевые слова перед `Цикл`, улучшить сообщение/span:
- “После `По <expr>` ожидается `Цикл`, найдено `<token>`”.

### Rule C (rewrite): `Если` header issues (`Если/Тогда`)
Фокус: улучшить сообщение и span для частых ошибок заголовка `Если`, например:
- отсутствие `Тогда` (или `Then`) после выражения условия;
- “обрыв” заголовка на неожиданном токене до `Тогда`.

Вывод:
- `ErrorType::InvalidSyntax`
- span: либо на месте, где ожидался `Тогда` (конец выражения условия), либо на неожиданном токене
- сообщение: “В конструкции `Если` ожидается `Тогда` после условия”.

### Rule D (rewrite): `Попытка` block issues (`Попытка/Исключение/КонецПопытки`)
Фокус: улучшить сообщение и span для ошибок структуры `Попытка`, например:
- незакрытый блок (отсутствует `КонецПопытки`);
- отсутствует `Исключение` (или `Except`) при наличии обработчика/ключевых слов.

Вывод:
- `ErrorType::MissingToken` или `InvalidSyntax` (в зависимости от доступных сигналов в дереве/ошибках)
- сообщение: “Не закрыт блок `Попытка` (ожидается `КонецПопытки`)” и/или “Ожидается `Исключение`”
- related info SHOULD сохраняться (если уже сформировано адаптером).

## Test Strategy
- Юнит-тесты в `syntax/` на маленьких snippets, проверяющие:
  - содержимое diagnostics (error_type/message),
  - точность span (указывает на корень проблемы),
  - отсутствие новых ошибок на валидном `Для`,
  - детерминированность.
  - ограничение “1 ошибка на строку” на случаях с несколькими сырыми ошибками.
