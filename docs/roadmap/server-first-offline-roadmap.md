# Roadmap: Server-first + Offline (локальный сервер)

**Статус:** 🔴 ПЛАН  
**Приоритет:** HIGH  
**Цель:** обеспечить две модели поставки в одном репозитории — server-first для большинства пользователей и полностью оффлайн режим через локальный сервер (для личного/enterprise использования) при сохранении тарификации и защиты критичного ядра.

---

## Контекст (текущее состояние)

- LSP/Web/CLI — отдельные процессы, но все они **включают inference‑ядро локально**.
- Критичная логика находится в `shared` и попадает в клиентские бинарники (LSP/CLI), что **не совместимо** с тарификацией и защитой IP.
- ADR-001 фиксирует server-first подход и тонкий клиент как целевую модель.

Ссылки:
- `docs/roadmap/ADR-001-server-vs-client-utf8.md`
- `docs/architecture/type_system_architecture.md`
- `docs/architecture/components-detailed.md`

## Целевой результат

Поддерживаются два режима:

1) **Server-first (SaaS/централизованный сервер)**  
   Клиенты (LSP/CLI) тонкие, все inference/semantic операции выполняются на сервере.  
2) **Offline (локальный сервер)**  
   Тот же API/протокол, но сервер запускается локально. Клиенты подключаются к `localhost`.  

**Важно:** это *не* “толстый клиент”. Оффлайн = локальный сервер, чтобы не ломать архитектуру и модель тарификации.

---

## Требования

### Функциональные

- Единый публичный API для hover/completion/diagnostics/signature help и индексации.
- Возможность переключать endpoint (SaaS ↔ localhost) без изменения клиента.
- Разделение “контрактов” и “ядра” так, чтобы клиенты **не содержали inference‑логики**.
- Поддержка workspace‑сессий: загрузка конфигурации, инкрементальные изменения файлов.
- Инструменты тарификации: авторизация, квоты, учёт запросов.

### Нефункциональные

- **Right-Sized Architecture:** минимальное число компонентов; без лишних сервисов.
- Стабильный UX в IDE (latency приемлем, кэширование на стороне сервера).
- Безопасность: ядро inference не поставляется клиенту.

---

## Предлагаемая архитектура

### 1) Разделение “контрактов” и “ядра”

- Выделить контрактный слой (DTO/IR/API‑типы) в отдельный crate/модуль:
  - `shared-contracts` (DTO, IR, протоколы, ошибки).
- Вынести inference‑ядро в server‑only crate:
  - `bsl-inference-core` (TypeResolver, AnalysisEngine, индексаторы, cache).
- Клиенты (LSP/CLI) зависят только от контрактов и клиента‑шлюза.

### 2) Gateway слой для клиентов

Единый интерфейс:
- `TypeSystemGateway` (trait)  
  - `LocalGateway` (server‑side)  
  - `RemoteGateway` (клиенты через HTTP/gRPC)

### 3) Серверное API

Минимальный набор:
- hover, completion, diagnostics, signature help
- indexing / workspace lifecycle
- configuration loading
- health / metrics / usage

### 4) Offline как локальный сервер

- Отдельный серверный бинарник, запускаемый локально.
- LSP/CLI подключаются по config к `http://localhost:PORT`.

## План работ (фазы)

### Phase 1: Контракты и границы
- Разделить `shared` на контрактный слой и inference‑ядро.
- Определить минимальный RPC/HTTP контракт (DTO для LSP‑запросов).

### Phase 2: Remote inference API
- Вынести текущие операции `TypeSystemService` в серверные handler‑ы.
- Реализовать `RemoteGateway` для LSP/CLI.

### Phase 3: Workspace/sync и индекс
- API для загрузки конфигурации и инкрементальных изменений.
- Серверное кэширование и восстановление состояния.
- Связать с `docs/roadmap/disk-cache-platform-config-parsing-roadmap.md`.

### Phase 4: Тарификация и контроль
- Auth (API key/token), rate limiting, usage accounting.
- Логи/метрики по workspace/пользователю.

### Phase 5: Offline server packaging
- Локальный сервер + документация запуска.
- Профили конфигурации LSP/CLI (endpoint selection).

---

## Риски и ограничения

- Рост latency при удалённом inference без грамотного кэширования.
- Сложность синхронизации workspace (особенно больших конфигураций).
- Дублирование логики на стороне клиента/сервера при отсутствии чётких границ.
- Повышенная сложность CI (две модели поставки).

---

## Открытые вопросы

- Должен ли offline режим требовать лицензию (lease) или быть free‑for‑dev?
- Как хранить/обновлять конфигурацию для SaaS режима (upload vs gateway)?
- Нужен ли fallback “толстого клиента” для полностью изолированных окружений?

---

## Критерии успеха

- Клиентские бинарники не содержат inference‑ядро.
- Один и тот же LSP/CLI работает с удалённым и локальным сервером.
- Возможна тарификация и метрики usage на стороне сервера.
