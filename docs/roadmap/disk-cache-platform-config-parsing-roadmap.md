# Roadmap: Дисковый кэш парсинга платформенной документации и конфигурации

**Статус:** 🔴 ПЛАН  
**Приоритет:** HIGH  
**Цель:** ускорить LSP/CLI и тесты за счёт переиспользования результатов парсинга `syntax_helper` (платформы) и выгруженных конфигураций, с корректной инвалидацией и поддержкой нескольких платформ/конфигураций на одном компьютере.

---

## Контекст (текущее состояние)

- Платформенные типы и методы подгружаются через `SyntaxHelperLoader` и конвертируются в `RawTypeData`, после чего строится `SignatureIndex` (единственный источник платформенных методов).
- Для тестов уже есть “переиспользование внутри одного test-бинаря” через `LazyLock`, но между разными integration test бинарями (`backend/tests/*.rs`) общий in-memory кэш невозможен: это разные процессы.

---

## Требования

### Функциональные

- Должен существовать общий механизм дискового кэша, который:
  - кэширует результаты парсинга/индексации платформы и конфигурации;
  - автоматически инвалидируется/пересобирается при изменении источников;
  - поддерживает одновременное существование нескольких платформ и конфигураций;
  - безопасен при параллельных запусках (несколько процессов/тестов).

### Нефункциональные

- **Right-Sized Architecture:** один понятный слой кэша, без множества “мини-сервисов”.
- **Честная проверка:** корректность подтверждается тестами и проверками (grep/сборка) перед отчётами.
- **Никаких демонов:** без обязательного фонового сервера/демона; всё работает “check-on-use”.

## Архитектура (предпочтительный вариант)

### Два слоя кэша

1) **Слой A: результат парсинга (самый дорогой I/O)**
   - Platform: сериализованный результат парсинга `syntax_helper` (или нормализованная DB).
   - Config: сериализованный результат discovery/парсинга `Configuration.xml` (универсальные метаданные + module paths).

2) **Слой B: производные индексы (самое полезное для runtime)**
   - `Vec<RawTypeData>` (platform/config) и/или готовые структуры для `SignatureIndex`.
   - (опционально) “snapshot репозитория”, если это совместимо с текущими структурами.

**Почему так:** слой A минимизирует повторный чтение/парсинг огромного числа файлов, а слой B минимизирует время до готового `SignatureIndex/Repo` для LSP/валидации.

### Ключи кэша (multi-platform + multi-config)

Каждый артефакт кэша адресуется ключом:
- `schema_version` (инкремент при изменении формата/семантики кэша);
- `source_kind` (`platform`/`config`/`combined`);
- `source_identity`:
  - Platform: canonical path к `syntax_helper` + извлечённая версия платформы (если доступно);
  - Config: canonical path к конфигурации + идентификатор/версия из `Configuration.xml` (если доступно);
- `source_fingerprint`: быстрый отпечаток содержимого (mtime/size + fallback на хеш содержимого при необходимости);
- `settings_fingerprint`: параметры парсинга/оптимизаций/локаль/фичи, которые влияют на результат.

### Инвалидация и пересборка “на ходу”

Модель: **check-on-use**.
- При запросе кэша вычисляется текущий fingerprint.
- Если кэш отсутствует или stale — выполняется builder и атомарно записывает новый артефакт.
- Опционально: **stale-while-revalidate** (использовать старый кэш и пересобрать в фоне), если это нужно для UX.

### Конкурентность и атомарность

- File-lock на ключ (один builder на один ключ).
- Запись через `tmp + atomic rename`.
- `manifest.json` рядом с артефактом: ключ, версия схемы, fingerprint, размер, время создания, статистика.

### Хранилище

- Базовый путь к кэшу: OS cache dir по умолчанию + override через env/CLI (например `BSL_CACHE_DIR`).
- Тесты используют тот же механизм; при необходимости могут направлять кэш в `target/` через override.

## Milestones

### D1: Базовый DiskCache API + manifest + locking
**Цель:** минимальный устойчивый слой “get-or-build” с атомарной записью.

**Критерии успеха:**
- есть единый модуль/интерфейс `DiskCache` (ключ → артефакт);
- есть `schema_version` и `manifest.json`;
- параллельные процессы не строят один и тот же ключ одновременно (file-lock);
- unit-тесты на atomic write и lock.

### D2: Кэш платформы (syntax_helper) — слой A
**Цель:** один раз парсить `syntax_helper` на ключ платформы и переиспользовать дальше.

**Критерии успеха:**
- при неизменном `syntax_helper` повторный запуск не делает полный парсинг;
- корректная инвалидация при изменении содержимого/пути/версии;
- интеграционный тест (можно на небольшой подвыборке `examples/syntax_helper` или синтетике).

### D3: Кэш платформы — слой B (RawTypeData/SignatureIndex)
**Цель:** быстро поднимать `SignatureIndex` без повторной конвертации.

**Критерии успеха:**
- время “готовности индекса” уменьшается относительно полного pipeline;
- тест: `SignatureIndex` содержит ожидаемые методы (например `Массив.Добавить`).

### D4: Кэш конфигурации (Configuration.xml + discovery) — слой A
**Цель:** переиспользовать результаты discovery/парсинга XML конфигурации.

**Критерии успеха:**
- корректная инвалидация при изменениях `Configuration.xml` и дерева метаданных;
- корректная поддержка нескольких конфигураций на одном ПК;
- интеграционный тест с `examples/conf` / `examples/conf_big` (если доступно).

### D5: Кэш конфигурации — слой B (RawTypeData + config methods index)
**Цель:** быстро поднимать “конфигурационные типы + методы из BSL-модулей”.

**Критерии успеха:**
- индекс экспортных методов конфигурации восстанавливается из кэша;
- инвалидация при изменениях `.bsl` модулей/путей;
- тест: переиндексация после изменения файла реально меняет результат.

### D6: Combined cache (platform + config → готовое состояние для анализа)
**Цель:** единый быстрый путь “запуск → готово к hover/validation”.

**Критерии успеха:**
- “combined” ключ учитывает оба источника и их настройки;
- корректно работает при нескольких платформах и нескольких конфигурациях;
- тесты могут использовать combined cache и не парсить 52k файлов на каждый test-бинарь.

### D7: Политики обновления и уборка
**Цель:** управляемость кэша.

**Критерии успеха:**
- настройка политики: `blocking` vs `stale-while-revalidate` (если включено);
- лимит размера/TTL и cleanup старых ключей;
- метрики/логирование: cache hit/miss, build time.
