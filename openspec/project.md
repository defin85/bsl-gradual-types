# Контекст проекта

## Назначение
BSL Gradual Type System — готовый для промышленного использования инструментарий градуальной типизации и статического анализа для языка 1С:Предприятие (BSL).

Основные цели:
- Давать полезную типовую информацию и диагностику для реальных BSL-кодовых баз
- Поддерживать анализ, чувствительный к потоку управления (flow-sensitive), и объединённые типы (union)
- Оставаться быстрыми на больших корпоративных проектах (инкрементальность + кэширование)
- Предоставлять несколько интерфейсов: CLI, LSP-сервер и веб-интерфейс для исследования типов
- Опционально использовать локальные ресурсы 1С: документацию платформы («синтаксис‑помощник») и метаданные конфигурации

## Технологический стек
- Rust (edition 2021), рабочее пространство Cargo (workspace) из нескольких крейтов (crates)
  - Требования: Rust 1.70+ (MSRV)
  - Инкрементальные вычисления: salsa
  - Парсинг: tree-sitter + вендоренная грамматика (`third_party/tree-sitter-bsl`)
  - Серверы/адаптеры: tokio, axum (веб), tower-lsp (LSP)
  - Логирование: tracing + tracing-subscriber
- Веб‑фронтенд: Leptos (CSR/WASM) через Trunk; Tailwind CSS
- VS Code расширение: TypeScript + esbuild, @vscode/test-electron; умеет бандлить Rust‑бинарники и использовать webview (WASM‑фронтенд)
  - Требования: Node.js 16+
- CLI инструменты: clap
- Тестирование/бенчмарки: `cargo test`, снапшоты `insta`, бенчмарки `criterion`

## Соглашения проекта

### Стиль кода
Rust:
- Форматирование: `cargo fmt`
- Линтинг: `cargo clippy --all-targets -- -D warnings`
- Ошибки: `thiserror` для библиотечных/доменной логики; `anyhow` на границах бинарников/CLI
- Логирование: `tracing`; избегать `println!` в боевом коде
- Производительность: избегать лишних аллокаций и клонирований (clone); горячие пути — по возможности без ввода/вывода (IO)

TypeScript (VSCode extension):
- «Линтинг» через проверку типов: `npm run lint` (tsc --noEmit)
- Активация расширения должна быть лёгкой; тяжёлая работа — в Rust‑сервисах

Именование и структура:
- Крейты (crates) в workspace используют префикс `bsl-*` (например, `bsl-backend`, `bsl-analysis-v2`)
- Предпочтение небольшим, сфокусированным модулям с чёткими границами между доменной логикой и вводом/выводом (IO) и адаптерами
- Фикстуры для тестов/примеров — минимальные и детерминированные

### Архитектурные подходы
Высокоуровневая структура workspace:
- `syntax/`: слой парсинга (интеграция tree-sitter, AST)
- `semantic/` + `semantic-diagnostics/`: семантическая модель и диагностики
- `analysis-v2/`: движок анализа/инференса типов (инкрементальность на salsa)
- `backend/`: веб‑сервер и LSP‑сервер (API + статика)
- `frontend/`: Leptos (WASM) UI
- `cli/`: командная строка
- `shared/`: общие типы/утилиты (в т.ч. совместимые с WASM)

Принципы:
- Доменная логика (анализ, типы, диагностики) — максимально чистая и тестируемая; ввод/вывод (IO) и побочные эффекты — на краях (backend/cli)
- Инкрементальность и кэширование — приоритет для отзывчивости на больших рабочих областях
- Экспорт возможностей через адаптеры: API, LSP, веб‑интерфейс и CLI
- Конфигурация backend по приоритету: CLI‑аргументы > переменные окружения > конфигурационный файл; конфиг по умолчанию: `backend/config.toml` (см. `CONFIG.md`)

### Стратегия тестирования
Rust:
- Модульные тесты внутри крейтов (на уровне модулей)
- Интеграционные тесты в `tests/` и в `*/tests/`
- Снапшот‑тесты через `insta`, где важна стабильность вывода
- Бенчмарки через `criterion` для критичных по производительности компонентов

VSCode extension:
- `npm test` запускает тесты расширения через @vscode/test-electron
- Покрытие: `npm run test:coverage` (c8)

Рекомендации:
- Новые правила анализа/диагностики должны иметь регрессионные тесты на небольших BSL‑сниппетах
- Тесты должны быть детерминированными; избегать сети и флакеров из‑за времени

### Работа с Git
Правила контрибьюта и проверок описаны в `CONTRIBUTING.md` (формат commit message, области (scopes), чек‑листы).

Текущее состояние репозитория:
- Основная ветка: `master` (пока единственная)

Кратко:
- Формат коммитов: `type(scope): short description` (см. `CONTRIBUTING.md`)
- Перед PR (pull request) / публикацией изменений: `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test`
- Если появятся feature‑ветки, используем `feature/<name>` (как в примерах в `CONTRIBUTING.md`)

Процессные инструменты:
- Предложения изменений на основе спецификаций живут в `openspec/changes/` (см. `openspec/AGENTS.md`)
- Трекинг задач — `bd` (beads) через task graph в `.beads/`

## Доменный контекст
Язык:
- 1С:Предприятие BSL (`.bsl`)

Типичные локальные входные данные/ресурсы:
- Экспорт документации платформы («синтаксис‑помощник»), например `examples/syntax_helper/rebuilt.shcntx_ru`
- Метаданные конфигурации 1С, корневой файл — `Configuration.xml`

Ключевые понятия анализа:
- Анализ, чувствительный к потоку управления (flow-sensitive): типы переменных могут сужаться/расширяться по мере прохождения потока управления (control flow)
- Объединённые типы (union), в т.ч. с весами, используются для инференса и отображения в интерфейсе

## Важные ограничения
- Производительность и память критичны (целевой кейс: большие корпоративные кодовые базы)
- Кроссплатформенность (WSL/Windows/Linux): внимательно к путям и кодировкам
- Предпочтение локальным файлам для документации/конфигурации (без обязательной сети в рантайме)
- По возможности держать стабильными публичные интерфейсы (CLI флаги, API роуты, настройки VSCode)
- Требования по версиям платформы 1С пока не зафиксированы

## Внешние зависимости
- Документация платформы 1С («синтаксис‑помощник») и файлы конфигурации (предоставляются пользователем, не вендорятся)
- Вендоренная tree-sitter грамматика: `third_party/tree-sitter-bsl`
- Инструменты Node.js для сборки/тестов `vscode-extension/`
