# Change: add-mcp-ui-dashboard

## Зачем
Разработчику нужен наглядный способ проверить, как `bsl-agent` (MCP) видит проект: готовность сессий, прогресс job’ов, состояние кэша и факт загрузки `syntax_helper`/конфигурации (чтобы быстро ловить ошибки вида “Тип `ТаблицаЗначений` не найден”).

При этом важно:
- модель запуска **per-agent** (каждый Codex/агент поднимает свой `bsl-agent` по stdio);
- UI для MCP **строго read-only**;
- UI должен быть **единым** с текущим Web UI (`bsl-web-server`) и использовать существующий артефакт `frontend → target/site` как “единую точку ответственности UI”.

## Что меняется
- `bsl-agent` получает **опциональный локальный HTTP UI** (только `127.0.0.1`), который:
  - раздаёт существующий SPA из `target/site`;
  - предоставляет read-only API `/api/mcp/*` для отображения состояния MCP (sessions/jobs/deps/meta/missing_inputs).
- `frontend` получает поддержку **capability detection** и режима “MCP”:
  - UI определяет, подключён ли он к `bsl-agent` или к `bsl-web-server`, и в MCP‑режиме не вызывает mutating API (`POST /api/snapshot/reload` и т.п.), а показывает только read-only экран.
- `bsl-web-server` добавляет минимальный read-only эндпоинт `/api/mcp/status` (или совместимый), чтобы тот же UI мог работать “везде” и корректно деградировать, когда MCP‑данные недоступны.

## Влияние
- Затронутая спецификация: `openspec/specs/mcp-bsl-agent/spec.md` (добавляются требования про UI/эндпоинты).
- Затронутые компоненты (на стадии реализации): `bsl-agent`, `backend (bsl-web-server)`, `frontend`.
- Риски: безопасность (локальный сервер), путаница режимов UI (web-server vs agent), конфликт за общий кэш (LSP ↔ MCP). Эти риски адресуются в `design.md`.

## Не цели (Non-goals)
- UI не является MCP‑клиентом и не заменяет MCP Inspector.
- UI не запускает/не отменяет job’ы и не модифицирует workspace/кэш (строго read-only для MCP).
- Не вводим общий “daemon MCP для всех агентов” — остаёмся в модели per-agent.
