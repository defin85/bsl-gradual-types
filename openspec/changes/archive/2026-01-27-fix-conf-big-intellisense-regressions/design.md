# Design: устранение регрессий IntelliSense на `conf_big`

## Наблюдения (evidence)
### 1) Formatting: `-32600 Invalid request` при save
Пользовательский repro:
- включён `editor.formatOnSave` глобально;
- `editor.defaultFormatter` не задан;
- в Output (канал “BSL Analyzer”) появляются ошибки:
  `Request textDocument/formatting failed. Message: Invalid request. Code: -32600`.

В текущей реализации LSP обработчик formatting при выключенной настройке возвращает `invalid_request`,
что и проявляется как `-32600` вместо “не поддерживается”.

### 2) Локальная функция: ложный `UndeclaredVariable`
Файл:
`examples/conf_big/Documents/РеализацияТоваровУслуг/Forms/ФормаДокументаОбщая/Ext/Form/Module.bsl`
- вызов `... СписокВидимыхТабличныхЧастей()` на `#L23`,
- объявление `Функция СписокВидимыхТабличныхЧастей()` на `#L3635`.

Go to Definition по имени функции внутри модуля работает, но диагностика рассматривает идентификатор как переменную.

Гипотеза: путь инференса для `Expression::Call(Identifier)` ищет только “глобальные” функции/сигнатуры,
и не учитывает локальные функции текущего модуля как callable.

### 3) Definition по `CommonModules.*` не работает
Пример:
`РеализацияТоваровУслугФормы.ПриСозданииНаСервере(...)` на `.../Module.bsl#L19`
должно вести в `examples/conf_big/CommonModules/РеализацияТоваровУслугФормы/Ext/Module.bsl#L11`,
но definition “не найдено” и для `РеализацияТоваровУслугФормы`, и для `ПриСозданииНаСервере`.

Гипотеза: handler `textDocument/definition` не использует snapshot/metadata‑индекс для резолвинга конфигурационных модулей.

### 4) Формы: реквизиты/элементы не попадают в типовую модель
Форма `ФормаДокументаОбщая` имеет:
- реквизит `<Attribute name="СчетФактура" ...>` с типом `cfg:DocumentRef.СчетФактураВыданный` в `Form.xml`,
- элементы `<UsualGroup name="СчетФактураПросмотр">` и `<UsualGroup name="СчетФактураРедактирование">`.

Но в модуле формы:
- hover по `СчетФактура` остаётся без типа (VariableAccess),
- `Элементы.СчетФактураПросмотр` даёт “property not exists” при типе `ЭлементыФормы.Документы.РеализацияТоваровУслуг.ФормаДокументаОбщая`.

Гипотеза: конвертер форм:
- не мапит `UsualGroup` в UI-тип → элемент не попадает в properties `ЭлементыФормы.*`;
- не добавляет `form.attributes` в тип формы/контекст модуля формы → реквизиты формы не резолвятся как идентификаторы.

## Принципы фикса (MVP)
- **No stubs by default**: capability заявляется только когда реально поддержано.
- **Детерминизм**: формирование типов/символов для форм и common modules должно быть стабильным.
- **Минимальные точки интеграции**: использовать уже существующий парсер `Form.xml` и репозиторий raw types,
добавив недостающие связывания.

## Предлагаемые изменения (в apply‑стадии)
1) Formatting:
   - capability gating в `ServerCapabilities`;
   - при выключенном режиме отвечать без `INVALID_REQUEST`.
2) Локальные функции:
   - поднять сигнатуры процедур/функций модуля в локальный callable‑index до анализа тела;
   - инференс/валидация: `Identifier()` резолвится как вызов локальной функции, не как переменная.
3) Definition:
   - резолвинг `CommonModules.<Name>` → файл модуля;
   - резолвинг `CommonModules.<Name>.<ExportProc>` → location объявления.
4) Формы:
   - `Элементы.*`: добавить `UsualGroup` и другие необходимые kinds в маппинг;
   - реквизиты формы: добавить `Form.xml` attributes в тип формы/контекст видимости модуля формы.
