# Roadmap: Типы из форм конфигурации (UI + данные формы)

**Статус:** 🟡 В РЕАЛИЗАЦИИ (MVP готов, расширения — по мере надобности)  
**Приоритет:** HIGH  
**Цель:** чтобы анализ кода в *модулях форм* корректно различал:

- **типы конфигурации** (в модуле объекта/менеджера): табличные части → `ТабличнаяЧасть<...>`
- **типы данных формы** (в модуле формы): табличные части → `ДанныеФормыКоллекция<...>`
- **UI-типы элементов формы** (через `Элементы.<Имя>`): `ТаблицаФормы/ПолеФормы/ГруппаФормы/...` (из syntax helper)

Ключевой принцип: **все типы должны попадать в `TypeRepository`** (как `RawTypeData`) и резолвиться через существующий доменный pipeline.

---

## Контекст и пример

Пример формы: `examples/conf/conf_test/Documents/ЗаказНаряды/Forms/ФормаДокумента/Ext/Form.xml`.

В форме есть таблицы:
- `Table name="Работы"` с `DataPath=Объект.Работы`
- `Table name="Стороны"` с `DataPath=Объект.Стороны`

Особенность 1С:
- `ДокументОбъект.*` / `ДокументСсылка.*` → ТЧ имеют тип `ТабличнаяЧасть<...>`
- *в форме* (данные формы) те же ТЧ представлены как `ДанныеФормыКоллекция<...>`

Типы `ТабличнаяЧасть` и `ДанныеФормыКоллекция` приходят из syntax helper, а структура строк/атрибутов берётся из конфигурации.

---

## Набор синтетических типов (в репозитории)

Для каждой формы создаём дополнительные `RawTypeData`:

1) **Тип формы (контекст модуля формы)**
- Имя: `Формы.<Коллекция>.<ИмяОбъекта>.<ИмяФормы>`
- Пример: `Формы.Документы.ЗаказНаряды.ФормаДокумента`
- Свойства: реквизиты формы (из `<Attributes>`) + “привязанные” реквизиты по `DataPath` (например `Работы`, `Стороны`)

2) **Тип “данных формы” для объекта (`Объект` в модуле формы)**
- Имя: `ДанныеФормыОбъект.<Коллекция>.<ИмяОбъекта>`
- Пример: `ДанныеФормыОбъект.Документы.ЗаказНаряды`
- Свойства: реквизиты метаданных (как в конфигурации) + табличные части, но с типом `ДанныеФормыКоллекция<Строка...>`

3) **Контейнер UI-элементов формы (`Элементы`)**
- Имя: `ЭлементыФормы.<Коллекция>.<ИмяОбъекта>.<ИмяФормы>`
- Пример: `ЭлементыФормы.Документы.ЗаказНаряды.ФормаДокумента`
- Свойства: все элементы формы по `name` из `<ChildItems>`; тип каждого элемента — UI-тип из syntax helper

## Milestones

> Примечание по процессу: чтобы не “делать по чуть‑чуть везде”, этапы стоит закрывать **вертикальными срезами** (парсинг → RawTypeData → загрузка → резолвинг/инференс → тесты).

### F1: Полный парсинг элементов формы (ChildItems + DataPath)

**Цель:** извлечь все элементы формы и их `DataPath` (для UI-слоя и привязок к данным).

**Изменения:**
- Расширить парсер форм так, чтобы он парсил:
  - рекурсивно `ChildItems`
  - `Table` + его дочерние элементы (колонки) с `DataPath`
  - любые элементы с `name`/`id`/`DataPath`
- В `FormMetadata` добавить структуру для элементов:
  - `elements: Vec<FormElementBinding>` (kind, name, id, data_path, children/columns)

**Оценка:** 4–6 часов | **Риск:** Средний (сложность XML структуры)

**Критерии успеха:**
- `FormParser` достаёт `Table` “Работы/Стороны” и их `DataPath` из `Form.xml` примера.
- `FormParser` достаёт `DataPath` у вложенных элементов таблицы (колонок), например:
  - `РаботыНомерСтроки` → `Объект.Работы.LineNumber`
  - `РаботыВидРаботы` → `Объект.Работы.ВидРаботы`
- Unit/Integration тест на реальном `Form.xml`.

---

### F2: Генерация и загрузка синтетических типов формы в TypeRepository

**Цель:** обеспечить “все типы в репозитории” и разделить “форма vs конфигурация”.

**Изменения:**
- При индексации конфигурации (после `discover_forms`) генерировать дополнительные `RawTypeData`:
  - тип формы (`Формы.*`)
  - тип данных формы объекта (`ДанныеФормыОбъект.*`)
  - тип контейнера элементов (`ЭлементыФормы.*`)
- Для строк табличных частей формы использовать `TabularRowType` из метаданных + **временно только** системное поле `LineNumber: Число` (остальное — позже).

**Оценка:** 6–10 часов | **Риск:** Средний (склейка данных формы ↔ метаданные)

**Критерии успеха:**
- `TypeRepository.find_type("Формы.Документы.ЗаказНаряды.ФормаДокумента")` возвращает `RawTypeData` с properties `Объект/Работы/Стороны`.
- `TypeRepository.find_type("ДанныеФормыОбъект.Документы.ЗаказНаряды")` содержит свойства `Работы/Стороны` типа `ДанныеФормыКоллекция<...>`.
- `TypeRepository.find_type("ЭлементыФормы.Документы.ЗаказНаряды.ФормаДокумента")` содержит свойства UI-элементов:
  - `Работы: ТаблицаФормы`
  - `Номер: ПолеФормы`
  - `Страницы/ГруппаРаботы: ГруппаФормы`

---

### F3: Syntax helper — извлечение “Элементы коллекции” и generic item type

**Цель:** получать `ДанныеФормыЭлементКоллекции<T>` без угадываний.

**Изменения:**
- В парсере syntax helper извлечь метаданные “Элементы коллекции: <Type>” для типов-коллекций.
  - Если такого блока нет, допускается fallback через return type `Получить()` (но только как резервный путь).
- Сохранить в `RawTypeData`/доп. структуре поле вида `collection_item_type: Option<String>`.

**Оценка:** 6–12 часов | **Риск:** Средний (варианты разметки справки)

**Критерии успеха:**
- Для `ДанныеФормыКоллекция` в данных платформы найден `collection_item_type == "ДанныеФормыЭлементКоллекции"`.
- Для типа без блока “Элементы коллекции” `collection_item_type` может быть выведен из return type метода `Получить()`,
  но только если return type соответствует реальному типу из базы syntax helper (чтобы не подхватить свободный текст).

---

### F4: Generic-подстановка item type для коллекций (все типы, не только формы)

**Цель:** чтобы методы коллекций корректно возвращали item type с параметром `T`.

**Изменения:**
- В `TypeMetadataLookup`/generic обработке добавить правило:
  - если базовый тип — generic collection и `collection_item_type` известен,
    то для `Получить()`/итерации/аналогичных методов return type → `collection_item_type<T>`.

**Оценка:** 4–8 часов | **Риск:** Средний (совместимость со старыми типами)

**Критерии успеха:**
- Для `ДанныеФормыКоллекция<СтрокаРаботы>` метод `Получить()` возвращает `ДанныеФормыЭлементКоллекции<СтрокаРаботы>`.

---

### F5: Инжект контекста формы в анализ (SymbolTable для FormModule)

**Цель:** в модуле формы резолвить:
- `Объект.Работы` → `ДанныеФормыКоллекция<...>`
- `Работы` (реквизит формы) → `ДанныеФормыКоллекция<...>`
- `Элементы.Работы/Номер/Страницы/...` → UI-типы элементов формы (`ТаблицаФормы/ПолеФормы/ГруппаФормы`)

**Изменения:**
- Определять контекст файла как `FormModule` по пути (уже поддерживается через `CodeLocation`).
- До инференса выражений засеивать `SymbolTable`:
  - `Объект: ДанныеФормыОбъект.*`
  - реквизиты формы (`Работы`, `Стороны`, …) из `Формы.*`
  - `Элементы: ЭлементыФормы.*`

**Оценка:** 6–12 часов | **Риск:** Средний (точка интеграции Ast→IR)

**Критерии успеха:**
- Интеграционный тест на файле `...Forms/.../Ext/Form/Module.bsl` (примерная конфигурация), где:
  - `Объект.Работы` имеет тип `ДанныеФормыКоллекция<...>`
  - `Элементы.Работы` имеет UI-тип
  - `Элементы.Номер` имеет UI-тип поля формы

> Примечание: текущий BSL-парсер в репозитории — заглушка, поэтому тест проверяет seeding контекста
> через `file_path` (чтобы сработал `FormModule`) и синтетический AST. Реальный e2e-тест “парсинг BSL
> из файла → IR” возможен только после появления полноценного парсера.

### F6: “Все системные поля” строки табличной части в форме

**Причина:** источник истины и полный список полей требуют отдельного исследования.

**На сейчас:** добавляем только `LineNumber: Число` (подтверждено в `Form.xml`).
