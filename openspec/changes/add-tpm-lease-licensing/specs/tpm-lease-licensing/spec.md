## ADDED Requirements

### Requirement: Лицензия привязана к TPM 2.0 ключу устройства
Система MUST привязывать лицензию к ключу TPM 2.0 устройства через идентификатор `tpm_pubkey_hash`.

Система MUST принимать renew только при доказательстве владения соответствующим TPM-ключом (challenge-response подписью).

#### Scenario: Renew успешен с правильным TPM-ключом
- **GIVEN** установлен валидный `license.lic`, привязанный к `tpm_pubkey_hash` устройства
- **WHEN** клиент проходит renew challenge и подписывает его соответствующим TPM-ключом
- **THEN** сервер выпускает новый lease и возвращает обновлённый `license.lic`

#### Scenario: Renew отклоняется при несовпадении TPM-ключа
- **GIVEN** `license.lic` привязан к одному `tpm_pubkey_hash`
- **WHEN** renew-запрос подписан другим ключом
- **THEN** сервер отклоняет renew и не продлевает `expires_at`

### Requirement: Политика lease и оффлайн-работы фиксирована
Система MUST поддерживать срок lease 30 календарных дней с момента последнего успешного renew/activate.

Система MUST разрешать запуск без сети до `expires_at`.

Система MUST предоставлять grace period 7 календарных дней после `expires_at`.

Система MUST применять hard-fail (полный отказ запуска) после окончания grace period.

#### Scenario: Оффлайн-запуск до истечения lease
- **GIVEN** `license.lic` валиден и текущее время меньше либо равно `expires_at`
- **WHEN** продукт запускается без доступа к сети
- **THEN** запуск разрешён

#### Scenario: Запуск в grace period
- **GIVEN** `expires_at` уже наступил, но с его момента прошло не более 7 календарных дней
- **WHEN** продукт запускается
- **THEN** запуск разрешён в рамках grace period

#### Scenario: Запуск после окончания grace period
- **GIVEN** с момента `expires_at` прошло более 7 календарных дней
- **WHEN** продукт запускается
- **THEN** продукт завершает запуск с hard-fail

### Requirement: Потоки activate/renew не содержат данных 1С
Система MUST формировать `activation_request` и renew payload без данных 1С, включая пути, содержимое и пользовательские артефакты.

Система MUST поддерживать online API-обмен и контролируемый offline-обмен формата request/response через поддержку.

#### Scenario: Activation request не содержит данных 1С
- **GIVEN** пользователь выполняет `product license activate`
- **WHEN** формируется `activation_request`
- **THEN** request содержит только лицензирующие данные (например, TPM public key/hash, nonce, метаданные версии) и не содержит данных 1С

### Requirement: Лицензирование не требует постоянного локального daemon
Система MUST выполнять валидацию лицензии и операции лицензирования во встроенной библиотеке и CLI, без требования постоянно работающего отдельного локального license-daemon.

#### Scenario: Базовые операции лицензии доступны без daemon
- **GIVEN** установлен продукт с лицензирующей библиотекой
- **WHEN** пользователь запускает `license status`, `license activate`, `license renew` или `license diag`
- **THEN** команды выполняются без требования отдельного постоянно запущенного локального процесса лицензирования

### Requirement: Enterprise VM с passthrough TPM поддерживается
Система MUST поддерживать активацию и renew в enterprise VM-сценарии при наличии passthrough TPM 2.0, удовлетворяющего требованиям лицензирования.

#### Scenario: Активация в VM с passthrough TPM
- **GIVEN** продукт развёрнут в VM, где TPM 2.0 доступен через passthrough
- **WHEN** пользователь выполняет активацию лицензии
- **THEN** активация проходит по тем же правилам TPM binding, что и на физическом хосте

### Requirement: Re-host и ротация ключей управляются сервером
Система MUST иметь серверно-управляемый процесс re-host для сценариев замены/поломки оборудования.

Система MUST поддерживать ротацию ключей подписи лицензий через версионированные публичные ключи в клиенте.

#### Scenario: Re-host переносит лицензию на новое устройство
- **GIVEN** исходное устройство недоступно или заменено
- **WHEN** support выполняет re-host по регламенту
- **THEN** старая привязка деактивируется, а новая лицензия выпускается для нового TPM binding

#### Scenario: Клиент валидирует лицензию после ротации ключа
- **GIVEN** вендор выполнил ротацию ключа подписи и выдал лицензию с новым `kid`
- **WHEN** клиент валидирует новую лицензию
- **THEN** проверка подписи проходит с использованием соответствующего публичного ключа из доверенного набора
