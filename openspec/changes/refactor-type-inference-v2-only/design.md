# Дизайн: v2‑only inference и удаление `bsl-semantic`

## Принцип
Одна система вывода типов должна иметь одну «истину»: один pipeline, один набор правил, один источник данных для IDE‑фич.

## Минимальный внутренний IR (в v2)
В рамках v2‑only архитектуры мы сохраняем IR, но делаем его **минимальным** и **внутренним**:
- IR существует только как артефакт v2 queries (не как отдельный пользовательский слой/крейt с собственными правилами).
- IR **не выполняет вывод типов** и не содержит «эвристик inference». Он описывает структуру и связи, необходимые downstream этапам.

### IR схема (MVP)
Ниже перечислен минимальный “контракт” IR для поддержки IDE‑фич без альтернативных пайплайнов.

#### 1) Текст и позиции
- IR MUST хранить позиции узлов в **byte offsets** относительно исходного текста файла (например, `start_byte/end_byte`).
- Преобразование byte offsets → LSP UTF‑16 `Position` MUST выполняться через v2 positioning/line-index слой (единый для всего pipeline).
- IR MUST быть привязан к конкретной версии содержимого файла (через v2 snapshot/revision).

#### 2) Области видимости и символы
IR MUST явно моделировать:
- `ScopeId` и иерархию scope’ов (parent/children).
- `SymbolId` и таблицу символов со следующими видами:
  - `Function` / `Procedure` (с флагом export, параметрами, decl span),
  - `Parameter`,
  - `LocalVariable` (минимум: имя + decl span + scope),
  - (опционально) `Global`/module-level declarations, если это нужно для текущих IDE‑фич.

IR SHOULD содержать ссылки “use → declaration” там, где это возможно дешёво и детерминированно:
- `Identifier` может быть `Unresolved(name)` либо `Resolved(SymbolId)` — но **резолвинг типов** не происходит на этом уровне.

#### 3) Выражения (нормализованная форма для completion v2)
IR MUST предоставлять выражения в виде дерева/графа `ExprId` с минимум следующими узлами:
- `Identifier { name | symbol_ref }`
- `MemberAccess { base: ExprId, member: Name }` (точка)
- `Call { callee: ExprId, args: Vec<ExprId> }`
- `IndexAccess { base: ExprId, index: ExprId }` (квадратные скобки)
- `Grouping { inner: ExprId }` (скобки)
- `Literal { kind }`
- `New { type_name: String, args: Vec<ExprId> }` (конструктор)

IR MUST сохранять span для каждого `ExprId`, чтобы receiver extraction был корректен на неполном коде.

#### 4) Операторы/statement’ы (минимум для scoping + будущего CFG)
IR SHOULD иметь минимальную модель statement’ов (или эквивалентную структуру), достаточную для:
- построения scope’ов (вход/выход из блоков),
- извлечения target/value в присваивании,
- поддержки базовых диагностик,
- будущего построения CFG.

Минимальный набор statement‑форм (MVP) SHOULD включать:
- `Assignment { target: ExprId, value: ExprId }`
- `VarDeclaration { name, initializer?: ExprId }`
- `If { condition: ExprId, then_block, else_block? }`
- `While { condition: ExprId, body }`
- `For { ... }` (если поддерживается в парсере)
- `Return { value?: ExprId }`
- `Block { statements: Vec<StmtId> }`
- `FunctionDecl` / `ProcedureDecl` (как корневые элементы с собственным scope)

### Инварианты (чтобы не было “костылей”)
#### Детерминизм
- IR MUST быть детерминированным для одинакового входного текста и одинакового deps snapshot.
- Порядок обхода/нумерации узлов MUST быть фиксированным (например, pre-order по AST).

#### Идентификаторы
- `ExprId`/`StmtId`/`ScopeId`/`SymbolId` MUST быть плотными индексами (или эквивалентом) и MUST быть валидны **только в рамках одного v2 snapshot**.
- Между запросами IDE (completion → resolve → hover) сервер MUST использовать один и тот же v2 snapshot или передавать/проверять `revision` так, чтобы идентификаторы не “утекали” между ревизиями.
- Для межзапросной идентификации (например, `completionItem/resolve`) MUST использоваться стабильный `CandidateId` (семантический ключ), а не прямой `ExprId`.

#### Запрет на inference внутри IR
- IR MAY хранить “явные аннотации” (например, текст type hint), но MUST NOT преобразовывать их в `TypeResolution` и MUST NOT выбирать facets.
- Любые `TypeResolution`/certainties/metadata lookups вычисляются только как часть v2 inference поверх IR.

### Что MUST уметь минимальный IR (MVP для IDE‑фич)
- **Scope/binding модель**: объявления переменных/параметров/процедур/функций и их области видимости.
- **Стабильные идентификаторы узлов** в рамках одного snapshot (для `completionItem/resolve`, hover, переходов).
- **Связь с текстом**: корректные ranges/позиции (LSP UTF‑16 ↔ внутренние offsets), чтобы ответы IDE не «уезжали».
- **Нормализованные формы выражений** для extraction receiver‑выражения в completion v2:
  - идентификаторы, member access, вызовы, индексирование, скобки/группировка,
  - цепочки вида `a.b().c[d].e`.
- **Минимальная семантика управления**: достаточно структуры блоков для базовых диагностик и будущего CFG (без обязательной реализации CFG в этом change).

### Что MUST NOT делать IR
- Не резолвить типы и не выбирать фасеты (это делает v2 inference поверх IR, используя deps snapshot).
- Не ходить напрямую в файловую систему/кэш (только данные из v2 окружения и deps snapshot).
- Не иметь альтернативного пути «если чего-то нет — попробуем эвристику» (без костылей/фолбеков).

## Целевые границы ответственности
- `bsl-syntax`: парсинг/AST, инкрементальность на уровне tree-sitter.
- `bsl-analysis-v2`: **единственный** pipeline вычисления IR/диагностик/типовой информации для IDE‑фич; владение queries и их согласованностью.
- `bsl-shared`: доменные типы (`TypeResolution`, `TypeResolver`, репозитории), DTO и общие утилиты.
- `bsl-backend`: адаптеры (LSP/HTTP), orchestration (writer thread, snapshots), форматирование результата для клиентов.

## Что делаем с AST→IR
Есть два валидных варианта. В рамках этого change выбираем один и фиксируем в реализации.

### Вариант A: AST→IR как часть `bsl-analysis-v2` (ВЫБРАНО)
- Перенести код конвертера AST→IR из `bsl-semantic` внутрь `bsl-analysis-v2` (например, модуль `ast_to_ir`).
- Вся логика, которая зависит от `TypeResolver`/`TypeMetadataLookup`, живёт в v2 pipeline как query‑этапы (или как чистые функции, но используемые только v2).

Плюсы:
- единое место, единый контракт, меньше crate‑границ.
Минусы:
- рост объёма `bsl-analysis-v2` (но это осознанная концентрация логики).

### Вариант B: выделить AST→IR в новый «нейтральный» crate (например, `bsl-ast2ir`) (НЕ В SCOPE)
- Удалить `bsl-semantic`, но вынести AST→IR в новый crate без inference‑эвристик.
- `bsl-analysis-v2` использует этот crate как зависимость.

Плюсы:
- чище разделение «конвертация» vs «вывод типов».
Минусы:
- новая граница crate; риск повторного появления эвристик «в конвертере».

## Решение
В рамках данного change мы реализуем Вариант A: перенос AST→IR внутрь `bsl-analysis-v2`.
Это осознанно «концентрирует» pipeline в одном месте и исключает повторное появление альтернативных путей вывода типов.

## Удаление legacy
Удаляем кодовые пути, которые:
- делают вывод типов вне v2 pipeline;
- содержат альтернативные кэши/IR‑построение, не синхронизированные с v2 snapshot.

## Архитектурный критерий «без костылей»
- Запрещаем альтернативные pipeline для inference (нет «если v2 недоступен — используем эвристику»).
- `TypeResolver` остаётся в домене, но используется как dependency v2 snapshot (через deps bundle), а не как обход v2.
- IDE‑фичи получают данные только из v2 snapshot (read-only) и остаются детерминированными.
