## Контекст
Flow-sensitive анализ (type narrowing / null-safety) в IDE и диагностике опирается на CFG, который хранится в `SemanticProgram.cfg` (v2 pipeline).

Текущее поведение имеет три проблемных класса:
1) `cfg: Option<_>` может быть `None`, что выключает flow-sensitive поведение целиком и часто “молча”.
2) Привязка “позиция → CFG контекст” использует эвристики (сдвиг назад на фиксированное окно, угадывание ветки), что приводит к нестабильным результатам на границах токенов, в пустых ветках и при частично распарсенном коде.
3) null-safety не обязана учитывать null-check в заголовках циклов, хотя это важно для реального BSL (например, `Пока x <> Null Цикл`).

Этот change — архитектурная стабилизация и уточнение контракта CFG как части v2 snapshot. Он целенаправленно меньше по объёму, чем общий change `integrate-flow-sensitive-v2-wiring`, и предназначен как его технический фундамент.

## Цели
- CFG в v2 snapshot всегда доступен: `SemanticProgram.cfg` = `Some(ControlFlowGraph)`.
- Контракт “byte offset → CFG node” детерминирован и bias-aware (completion vs hover vs diagnostics).
- null-safety учитывает null-check в заголовках циклов (`LoopHeader`).

## Не цели
- Не расширять список IDE‑фич (только стабилизировать базовый flow-sensitive слой).
- Не менять вывод типов/инференс и структуру deps snapshot.

## Решения

### 1) `cfg` всегда `Some`
Решение: строить минимум “скелет” CFG даже при отсутствии исполняемых конструкций:
- узлы `Entry`, `Exit`;
- ребро `Entry -> Exit`.

Следствие:
- consumers больше не используют `cfg == None` как сигнал отсутствия CFG;
- отсутствие “полезного” контекста выражается иначе (например, `node_at_byte_offset` не нашёл подходящий span или narrowing не дал более точного типа).

### 2) Spans как источник истины для веток/тел
Решение: `Conditional`/`LoopHeader` узлы получают span “шапки” (первая строка конструкции), а тело ветки/цикла должно попадать в отдельные CFG узлы.

Это позволяет:
- определять ветку/контекст по попаданию offset в span узлов тела;
- убрать runtime‑угадывание веток `then/else` по `else_start` и эвристику “окно назад”.

Для пустых веток/тел:
- добавлять placeholder узел с корректным span тела, чтобы mapping не деградировал.

### 3) Детерминированный API `node_at_byte_offset(offset, bias)`
Решение: централизовать выбор CFG узла по позиции в одном месте (в `ControlFlowGraph`), чтобы:
- не дублировать алгоритм по разным consumers;
- гарантировать одинаковое поведение (hover/completion/diagnostics).

Bias‑модель (минимум):
- `Exact` / “самый узкий span, содержащий offset” — базовый режим;
- `PreferLeft` (для completion на `.`) — интерпретировать позицию как относящуюся к выражению слева.

В этом change фокус на корректности/детерминизме. Оптимизация (интервальные индексы) допустима как следующий шаг, если profiling покажет необходимость.

### 4) Null-safety для `LoopHeader`
Решение: считать `LoopHeader { condition }` эквивалентом `Conditional { condition }` с точки зрения извлечения null-check переменной (например, `x <> Null`, `ЗначениеЗаполнено(x)`), и применять пометку non-null к successor’ам тела цикла.

## План миграции
1) Уточнить CFG builder: `cfg` всегда `Some`, поправить spans для header/body, добавить placeholder для пустых веток.
2) Добавить `node_at_byte_offset(..., bias)` и перевести runtime wiring (hover/completion) на него.
3) Расширить null-safety на `LoopHeader`.
4) Закрепить тестами.

## Риски и компромиссы
- Неправильные spans могут ухудшить качество narrowing. Митигировать тестами на границы токенов и пустые ветки.
- Расширение null-safety на циклы может изменить количество warning’ов. Это ожидаемое улучшение; закрепить golden/интеграционными тестами.
