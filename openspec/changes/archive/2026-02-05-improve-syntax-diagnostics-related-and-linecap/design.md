# Design: Нормализация синтаксических diagnostics (merge+rewrite+line-cap) и related enrichment

## Context
В `bsl-syntax` синтаксические diagnostics формируются несколькими источниками:
- tree-sitter `ERROR` узлы и `node.is_missing()` (структурные missing tokens);
- эвристики уровня IDE (semicolon, неполный `Новый`, и т.п.);
- rule-based post-processing (rewrite/enrich) для распознаваемых паттернов.

Сейчас rewrite/line-cap применяется только к части ошибок (parser-derived), а эвристики добавляются позже,
из-за чего общий контракт “≤1 синтаксическая ошибка на строку” не гарантируется для итогового списка.

## Goals
- Единый, детерминированный pipeline нормализации для всех синтаксических diagnostics.
- Строгий line-cap: не более 1 синтаксической диагностики на строку в итоговом `ParseResult.syntax_errors`.
- Обобщённое правило `Для`: “ожидается `Цикл`” + span на первый неожиданный токен, даже если это мусор.
- Related enrichment для структурных ошибок (минимум: `Попытка`), чтобы IDE могла показывать “Начало блока”.

## Non-Goals
- Изменение грамматики или полноценная токенизация всего языка.
- Авто‑фиксы.

## Proposed Pipeline
В `TreeSitterAdapter::convert_tree`:
1) Собрать **все** синтаксические diagnostics:
   - tree-sitter errors/missing;
   - IDE эвристики (semicolon/`Новый`).
2) `rewrite/enrich`:
   - применить rewrite правила (узкие и обобщённые);
   - при распознавании структурных ошибок добавить related, если его нет.
3) `line-cap`:
   - сгруппировать diagnostics по строке (через `LineIndex` и `span.start`);
   - оставить 1 на строку по приоритету.
4) `stable sort`:
   - сортировка по `(span.start, span.end, priority, message)` для детерминизма.

## Priorities (для line-cap)
Рекомендуемая политика (меньше — лучше):
1) `InvalidSyntax` (rewritten, конкретные сообщения и узкие spans)
2) `MissingToken` (структурные/незакрытые блоки)
3) `ParseError` (общий parser error)
4) IDE эвристики (`semicolon`, `Новый`) — если они представлены теми же `ErrorType`, маркировать их внутренним `kind`
   (например, enum `SyntaxDiagOrigin`) и учитывать как tie-breaker.

## Generalized `Для` rule
В заголовке `Для` после `По <expr>` ожидается `Цикл`.
Если между `По` и `Цикл` есть лишний токен:
- определить диапазон между `По` и `Цикл`;
- найти **первый токен** (идентификатор/число/символ) после пробелов;
- вывести `InvalidSyntax` с сообщением “После `По <выражение>` ожидается `Цикл`” и span на найденный токен.

## Masking (comments/strings)
Чтобы не матчить ключевые слова внутри строк/комментариев:
- построить `masked_line` той же длины, где:
  - всё после `//` заменено пробелами,
  - содержимое строковых литералов заменено пробелами,
  - индексы совпадают с оригиналом (span вычисляется по оригинальным индексам).

## Related enrichment
Если правило распознало незакрытый блок `Попытка`, но `related` пустой:
- добавить `RelatedInformation { message: \"Начало блока: Попытка\", span: <span на ключевое слово> }`.
