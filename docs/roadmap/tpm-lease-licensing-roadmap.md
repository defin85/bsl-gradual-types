# Roadmap: TPM-lease лицензирование (on-prem, 30 дней offline)

**Статус:** 🔴 ПЛАН  
**Приоритет:** HIGH  
**Цель:** ограничить использование продукта лицензией “1 машина = 1 лицензия” с обязательным TPM 2.0 и оффлайн-работой до 30 дней (lease), без передачи/обработки данных 1С и без постоянного локального license-daemon.

---

## Контекст и ограничения

- Продукт разворачивается on-prem у клиентов (Linux/Windows).
- Интернет обычно доступен, но требуется оффлайн-режим до 30 дней.
- TPM 2.0 обязателен (на первом этапе таргет только “железо”, без поддержки VM как целевой сценарий).
- Не распространяем и не встраиваем в поставку артефакты/данные 1С (BYO: клиент подключает сам).
- Контейнер/обфускация не дают DRM: цель лицензирования — повысить порог злоупотреблений, а не “сделать невзламываемо”.

---

## Целевой UX

### Активация (первый запуск)
1) Пользователь запускает `product license activate`.
2) Продукт генерирует `activation_request` (без данных 1С): публичный ключ TPM, nonce, метаданные версии.
3) Пользователь отправляет request в License API (или через offline-обмен “request -> response” через поддержку).
4) Получает `license.lic` и кладёт рядом/в стандартный путь. Продукт начинает работать.

### Обычный запуск
- Если `license.lic` валиден и `expires_at` не истёк — запуск без сети.
- Если до истечения осталось меньше порога (например, 7 дней) и сеть доступна — авто-renew lease.

### Оффлайн
- Без сети продукт продолжает работать до `expires_at` (30 дней от последнего renew).
- После `expires_at` действует grace period 7 дней.
- После окончания grace period: hard-fail (полный отказ запуска).

### Перенос/поломка железа
- Поддерживаем процесс re-hosting: “деактивировать старую привязку -> выдать новую лицензию”.
- Источник правды — сервер (через customer portal или поддержку).

## Архитектура (минимальный контур)

### 1) Лицензия как подписанный документ
- Формат: канонический JSON (строгий порядок полей) или CBOR.
- Подпись: Ed25519 (предпочтительно) или RSA-PSS.
- Публичный ключ вендора вшит в бинарник; приватный ключ хранится вне репозитория (KMS/HSM/офлайн-сейф).

Минимальные поля:
- `license_id`, `customer_id`
- `issued_at`, `expires_at`
- `product`, `edition`, `features`
- `device_binding`:
  - `tpm_pubkey_hash` (hash публичного ключа TPM)
  - (опционально) `tpm_attestation` / `device_cert_chain` (см. milestones)
- `signature` (над канонизированным payload)

### 2) Привязка к устройству через TPM
- На машине создаётся неэкспортируемая ключевая пара в TPM.
- Продукт может:
  - подписать challenge (доказательство владения ключом),
  - предоставить публичный ключ (или его хэш) для привязки лицензии.

### 3) Lease renew протокол

`POST /v1/license/renew`:
- Client -> Server: `license_id`, `nonce`, `challenge_request`, `tpm_pubkey` (при необходимости)
- Server -> Client: `challenge`
- Client -> Server: `signature = TPM.Sign(challenge)`
- Server -> Client: новый `license.lic` (expires_at = now + 30d)

Важно: сервер проверяет, что подпись сделана ключом, соответствующим `tpm_pubkey_hash` в текущей лицензии.

### 4) Без локального демона
- Встроенная библиотека лицензирования в продукт + CLI-команды:
  - `license status`
  - `license activate`
  - `license renew`
  - `license diag` (экспорт диагностического отчёта без данных 1С)

## Milestones (вертикальные срезы)

### L0: Спецификация и ADR
**Цель:** зафиксировать требования, угрозы, протокол и UX.
**Критерии успеха:**
- ADR по лицензированию (что защищаем / что не защищаем).
- Спецификация `license.lic` (формат, поля, канонизация, подпись).
- Спецификация API (`/activate`, `/renew`, коды ошибок, rate limiting).
- Зафиксирована политика истечения: grace period 7 дней, затем hard-fail.

### L1: Библиотека проверки лицензии (без TPM)
**Цель:** иметь стабильную и тестируемую валидацию `license.lic`.
**Критерии успеха:**
- Валидация подписи, срока, product/edition/features.
- Чёткие ошибки (invalid signature / expired / wrong product / tampered).
- Unit-тесты на парсинг/канонизацию/подпись (golden vectors).

### L2: TPM key management (Linux + Windows)
**Цель:** создать/прочитать TPM-ключ и уметь подписывать challenge.
**Критерии успеха:**
- Единый интерфейс `TpmSigner` с реализациями по ОС.
- Команда `license diag` показывает: TPM detected, pubkey hash, алгоритм.
- Документированы зависимости и требования (TPM 2.0 enabled, permissions).

### L3: Активация (request -> license)
**Цель:** реализовать первичную привязку лицензии к `tpm_pubkey_hash`.
**Критерии успеха:**
- `license activate` генерирует request и принимает/устанавливает `license.lic`.
- На сервере выдача лицензии возможна по request (минимальный admin-инструмент).
- В request нет данных 1С и нет пути/контента пользовательских файлов.

### L4: Renew lease (30 дней) + offline UX
**Цель:** продление лицензии без переактивации.
**Критерии успеха:**
- Авто-renew при наличии сети и близком истечении.
- Ручной `license renew`.
- Политика grace period: 7 дней после `expires_at`.
- Поведение при истечении grace period: hard-fail.
- Поведение при ошибках сети (retry/backoff, диагностика).

### L5: Anti-rollback времени (опционально, но желательно)
**Цель:** снизить ценность отката системных часов для обхода истечения.
**Критерии успеха:**
- Выбран механизм (TPM NV counter / sealed state / другой).
- Есть детерминированное поведение при сбросе TPM/NV (support flow).

### L6: Attestation “железо vs эмуляция” (опционально, зависит от боли)
**Цель:** усложнить использование софт-TPM/эмуляторов.
**Критерии успеха:**
- В request добавляется доказательство (quote/attestation).
- Сервер валидирует цепочку/политику (минимально: manufacturer allowlist).
- Описаны ограничения и поддерживаемые сценарии VM с passthrough TPM (enterprise).

### L7: Операционные процессы и ключи
**Цель:** сделать выпуск/перевыпуск/отзыв управляемыми.
**Критерии успеха:**
- Процесс key rotation (versioned public keys в клиенте).
- Portal/CLI для поддержки: re-host, disable, audit trail.
- Политики по rate limiting, abuse, логирование без персональных данных.

### L8: Сборка, дистрибуция, тестирование
**Цель:** поставить это в CI и в release-процесс.
**Критерии успеха:**
- Интеграционные тесты протокола renew (в CI можно через swtpm).
- Release checklist: не включать 1С-артефакты, сканирование содержимого дистрибутива.
- Документация для клиентов: требования TPM, активация, offline, перенос.

## Риски и компромиссы

- Клиент контролирует хост: возможен патч бинарника (цель — сделать это дороже, а не “невозможно”).
- TPM-экосистема разная на Windows/Linux; придётся инвестировать в диагностику и поддержку.
- Anti-rollback и attestation заметно усложняют реализацию и саппорт.

---

## Решения по открытым вопросам

- Поведение после истечения lease: hard-fail.
- Grace period: 7 дней.
- VM сценарий: допускается и поддерживается passthrough TPM (enterprise VM).
- По “офлайн-выдаче” через человека (без API доступа): решение пока не принято.

---

## Definition of Done

- Лицензия подписана, валидируется локально, привязана к TPM-ключу.
- Renew продлевает lease до 30 дней, без отдельного локального демона.
- После `expires_at` действует grace period 7 дней; по его окончании — hard-fail.
- В диагностике нет данных 1С; поставка не содержит 1С-артефактов.
- Описаны процессы re-host/rotation и минимальный tooling для поддержки.
