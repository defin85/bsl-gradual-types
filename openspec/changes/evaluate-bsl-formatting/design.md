# Design: formatting strategy for BSL

## Вопрос, который решаем
Какой форматтер BSL мы считаем “каноничным” для этого проекта и как он интегрируется в IDE (VS Code через LSP).

## Критерии выбора
- Детерминизм (одинаковый ввод → одинаковый вывод).
- Минимальный diff (не “переписывает” код целиком).
- Производительность (интерактивность).
- Корректность для BSL синтаксиса (включая директивы/препроцессор).
- Совместимость со стилем команды (настройки/конфиг).

## Варианты
Выбран вариант **A (AST‑based форматтер в Rust)**.

### A) AST‑based форматтер на базе tree-sitter + правила (выбран)
**Почему:**
- Полный контроль над детерминизмом и минимальным diff.
- Нет зависимости от внешних бинарников/лицензий/окружения пользователя.
- Можно эволюционировать по мере роста покрытия синтаксиса и требований.

**Trade-offs:**
- Существенная стоимость разработки/поддержки (покрытие всего BSL постепенно).
- Сложнее сохранить комментарии/директивы и “тонкую” структуру без переписывания текста.

**Стратегия поставки (итеративно):**
1) MVP: AST‑based reindent (пересчёт ведущих пробелов), удаление trailing whitespace, нормализация конца файла.
2) Расширение правил: пробелы вокруг операторов, переносы, выравнивание блоков, форматирование `Если/Тогда/КонецЕсли`, `Попытка/Исключение`, `Процедура/Функция`.
3) Range formatting (если будет корректная и предсказуемая модель на границах диапазона).

### B) Интеграция внешнего форматтера/инструмента (не выбрано)
**Почему не сейчас:**
- Риски по лицензии/распространению, кроссплатформенности и воспроизводимости результатов.
- Сложнее гарантировать отсутствие блокирующего I/O и контроль качества “минимального diff”.

### C) Отказ от встроенного форматирования (не выбрано)
**Почему не сейчас:**
- Не закрывает ожидания IDE‑grade UX и ломает целостность продукта (IntelliSense без formatting в IDE).

## Ожидания к форматированию (MVP scope)
- Отступы блоков и вложенности (включая директивы/препроцессорные блоки, где применимо).
- Удаление trailing whitespace.
- Нормализация конца файла (одна финальная `\\n`).

## Non-goals (MVP)
- Не менять регистр идентификаторов.
- Не перестраивать выражения и не менять порядок токенов.
- Не пытаться “чинить” синтаксически сломанный код (best-effort: не падать, вернуть либо пустой diff, либо предсказуемый отказ).

## Результат
Выбран вариант A. Следующий change на реализацию: `openspec/changes/add-bsl-lsp-formatting/`.
