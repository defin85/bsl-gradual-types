# Дизайн: межпроцедурный вывод return‑типа (multi-file) + overlay

## Цели

1) Дать стабильный, корректный вывод возвращаемых типов для пользовательских функций/процедур с межфайловыми вызовами.
2) Использовать существующую систему кэширования:
   - DiskCache для конфигурационных модулей и их индексации;
   - salsa/v2 snapshot для открытых файлов.
3) Сохранить известные типы даже при неопределённости и понижать уверенность до `InferredWeak`, а не “обнулять” результат.

## Наблюдения о текущей системе (grounding)

- Индексация BSL-модулей конфигурации уже строит `SignatureIndex` из экспортов (`config_methods`/`global_functions`) и уже кэширует `ParsedModuleData` в DiskCache (`config-module-parse`).
- `analysis-v2` (salsa) отвечает за IDE‑запросы и умеет жить на “открытых файлах”, но межпроцедурный вывод return-типа пользовательских функций в v2 pipeline не реализован.
- `SignatureIndex` — удобная точка стыка: в него уже попадают экспортные методы/функции конфигурации и глобальные функции из global common modules.

## Архитектура (2 контура)

### Контур A: конфигурация (persistent, межсессионный)

Источник: все BSL-модули конфигурации, которые уже индексируются `config_bsl_modules`.

1) Собираем декларации функций/процедур (включая `export` и локальные вспомогательные).
2) Собираем call graph между:
   - локальными вызовами внутри модуля;
   - квалифицированными вызовами в другие модули (`ИмяОбщегоМодуля.Метод()` / менеджеры);
   - вызовами платформенных функций (как “внешний источник”, без ребра в user graph).
3) Считаем return‑summaries фикс‑пойнтом:
   - строим SCC по графу пользовательских функций;
   - обрабатываем SCC в топологическом порядке;
   - внутри SCC используем worklist до стабилизации.
4) Экспортируем результаты:
   - для экспортных деклараций строим строковый `return_type` (union);
   - записываем в `SignatureIndex` как `MethodSignature.return_type`.

### Контур B: overlay для открытых файлов (in-memory, IDE)

Источник: набор открытых файлов в LSP (open files), которые могут быть изменены и ещё не сохранены на диск.

1) Для каждого открытого файла вычисляем локальный индекс экспортов и return‑summaries (включая локальные вспомогательные функции в файле).
2) Формируем overlay‑таблицу по всем open files и применяем её при резолве вызовов:
   - изменения в файле B должны влиять на типы вызовов в файле A (если оба открыты).
3) При отсутствии данных (например, не удалось определить global common module) — помечаем слабую уверенность, но не теряем известные типы.

## Модель данных: ReturnSummary

Внутренний домен для фикс‑пойнта:

- `known: Set<TypeAtom>` — множество известных конкретных типов (канонизированных строк).
- `has_dynamic: bool` — флаг неопределённости (встречены неразрешимые выражения/вызовы/динамика).

Правило объединения (join):

- `known = union(known_a, known_b)`
- `has_dynamic = has_dynamic_a || has_dynamic_b`

Финализация в строковый union:

- `known` нормализуется и сортируется детерминированно.
- если `known` пуст и `has_dynamic=true` → возвращаем `None` (как отсутствующий return type) или специальное значение (договориться на этапе реализации), но call-site получает `Unknown`.
- если `known` непусто → `return_type = known.join(" | ")` (даже если `has_dynamic=true`).

Семантика “dynamic/weak”:

- `has_dynamic=true` не уничтожает `known`;
- в IDE слой, когда тип получен из user-inference, certainty должен быть `Inferred`/`InferredWeak` (в зависимости от `has_dynamic`), а не `Known`.

## Разрешение вызовов (кратко)

- Неквалифицированный вызов `F()`:
  - если `F` — локальная функция в текущем модуле → ребро в граф (точный);
  - иначе считаем источник неопределённым (может быть глобальная функция из global common module), и выставляем `has_dynamic=true`.
- Квалифицированный вызов `Модуль.F()`:
  - если `Модуль` распознан как common module и `F` — экспорт → ребро к экспортной функции этого модуля;
  - иначе `has_dynamic=true`.

## Кэширование и инвалидация

- Используем существующий DiskCache для `ParsedModuleData` (per-module).
- Изменение формата данных должно вести к естественной инвалидации:
  - через обновление fingerprint/settings_fingerprint или schema.
- Контур B целиком в памяти и зависит только от salsa inputs (тексты open files + deps snapshot).

## Детальные trade-offs

- Мы сознательно не делаем полный flow-sensitive межпроцедурный анализ, чтобы сохранить производительность и простоту.
- Точность по выражениям возврата ограничена тем, что мы извлекаем (атомы типов + ссылки на вызовы). Это даёт большой выигрыш на “return f();” и “return x;” при адекватной типизации переменных, и безопасно деградирует на динамике.
