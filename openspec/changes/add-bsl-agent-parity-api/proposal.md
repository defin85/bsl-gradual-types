# Change: add-bsl-agent-parity-api

## Зачем
Сейчас HTTP UI в режиме MCP (`bsl-agent`) показывает служебные данные (сессии/jobs/snapshot), но не даёт ответ на ключевой вопрос: **какие типы реально доступны MCP** и какие результаты поиска/фильтрации видит агент.

Нужно, чтобы UI в MCP-режиме был **таким же**, как UI `bsl-web-server` (Dashboard/Карточки/Таблица/Граф + поиск/фильтры), но работал на данных текущей workspace-сессии `bsl-agent` и дополнительно позволял видеть особенности MCP (read-only, сессии, jobs).

## Что меняется
- `bsl-agent` получает read-only HTTP эндпоинты parity уровня “web-server API” в namespace `/api/mcp/*`, которые возвращают данные для UI (types/search/metrics) **из одной активной ready-сессии**.
- `frontend` (единый SPA) в MCP-режиме использует parity эндпоинты `/api/mcp/*` и показывает те же экраны, что и в режиме `bsl-web-server`, плюс MCP‑специфическую информацию.

Ключевое ограничение (согласовано):
- UI “аналитические” экраны работают **только когда существует ровно одна `ready=true` сессия** в `bsl-agent`.
  - Если `ready` сессий 0 или >1, UI показывает понятное сообщение и не пытается ходить в parity эндпоинты без `sessionId`.

## Не цели (Non-goals)
- UI не запускает/не отменяет job’ы и не делает mutating вызовов (остаётся строго read-only).
- Не добавляем UI‑селектор сессии: вместо этого требуем “ровно одна ready”.
- Не проксируем запросы в `bsl-web-server`: parity API обслуживается самим `bsl-agent` на данных его workspace.

## Влияние
- Затронутая спецификация: `openspec/specs/mcp-bsl-agent/spec.md` (добавляется требование parity HTTP API и правила выбора сессии).
- Затронутые компоненты на стадии реализации: `bsl-agent` (HTTP UI), `frontend` (режим MCP), документация `docs/roadmap/mcp-bsl-agent/api.md`.
