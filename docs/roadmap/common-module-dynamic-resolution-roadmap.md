# Roadmap: динамическое типизирование ОбщийМодуль(<строка>)

**Статус:** 🟡 В ПРОЦЕССЕ  
**Приоритет:** HIGH  
**Цель:** научить систему типов выводить тип общего модуля при вызове `ОбщегоНазначения.ОбщийМодуль("Имя")`, а при невозможности — честно возвращать union/Unknown.

---

## Контекст
- В конфигурации общие модули уже парсятся и им назначаются типы в TypeRepository.
- В коде используется динамический доступ через строку (`Вычислить(Имя)`), что ломает статический вывод типа.
- Требование: при строковом литерале вернуть тип общего модуля; при не‑литерале — union/Unknown.

**Точки входа (по репозиторию):**
- Анализ выражений/вызовов: `backend/src/application/ast_to_ir/expression_converter.rs`
- Type inference: `backend/src/application/ast_to_ir/type_inference.rs`
- TypeRepository и RawTypeData: `shared/src/domain/repository.rs`, `shared/src/domain/types/raw_data.rs`
- Парсинг метаданных (общие модули): `backend/src/data/loaders/config_metadata_parser/`
- Hover (проверка результата): `backend/src/helpers/hover_formatter/formatter.rs`

---

## Архитектурный принцип
- **Если строка — литерал:** пытаемся разрешить в конкретный тип общего модуля.
- **Если строка — не литерал:** отдаём **union/Unknown** с пониженной уверенностью.

---

## Milestones

### P1: Инфраструктура резолвинга строкового имени 🟡
**Цель:** получить из TypeRepository быстрый lookup “имя общего модуля → тип”.

**Подход:**
- Ввести индекс/lookup по типам общих модулей (по имени из метаданных).
- Хранить маппинг в памяти рядом с TypeRepository (v2 deps snapshot / SemanticDeps).
- Добавить утилиту поиска `find_common_module_type(name)` в application layer.

**Критерии успеха:**
- Есть функция `resolve_common_module("Имя") -> Option<TypeId/TypeResolution>`.
- Локальный поиск не зависит от дополнительных парсеров.

---

### P2: Спец‑кейс в inference для ОбщегоНазначения.ОбщийМодуль 🟡
**Цель:** выводить конкретный тип при литерале.

**Подход:**
- В анализе выражений распознавать вызов `ОбщегоНазначения.ОбщийМодуль(<arg>)`.
- Если `<arg>` — строковый литерал: резолвить через `resolve_common_module`.
- Если `<arg>` — не литерал: вернуть union/Unknown (или Known с низкой уверенностью).
- Добавить трассировку причины Unknown (динамическое имя).

**Критерии успеха:**
- Переменная, присвоенная из литерала, получает тип общего модуля.
- Для не‑литерала отображается честный “не удалось вывести”.

---

### P3: Совместимость с hover и diagnostics 🟡
**Цель:** чтобы вывод типа отражался в hover и не ломал существующие проверки.

**Подход:**
- Использовать существующие механизмы hover (TypeRepository/TypeMetadataLookup).
- Для Unknown/Union — корректно отображать причину.
- В hover добавить пояснение, что имя модуля динамическое (если применимо).

**Критерии успеха:**
- Hover по переменной показывает описание общего модуля (если резолвится).
- При Unknown/Union объясняется причина (динамическое имя).

--- 

### P4: Интеграция с резолвингом типов модулей 🟡
**Цель:** корректно определять тип общего модуля по имени в конфигурации.

**Подход:**
- Подтвердить, где именно хранится тип общего модуля в `RawTypeData` (kind/category/facets).
- Для CommonModule выбрать стабильный ключ сопоставления (русское имя).
- Зафиксировать формат имени в вызове `ОбщийМодуль("Имя")` и сопоставить с метаданными.

**Критерии успеха:**
- `ОбщийМодуль("УправлениеДоступом")` всегда резолвится в один и тот же тип.

## Тесты

- Unit: не‑литерал → union/Unknown.
- Integration: реальный конфиг с модулем `УправлениеДоступом`.

**Точки для тестов:**
