# Roadmap: Парсинг BSL-модулей конфигурации (методы, фасеты, валидация)

**Статус:** 🟡 В ПРОЦЕССЕ (MVP C1–C4 уже в коде)  
**Приоритет:** HIGH  
**Цель:** сделать так, чтобы код из выгруженной конфигурации (`*.bsl`) участвовал в **валидации** и давал **методы/сигнатуры** для `hover/completion/validation`, с корректной привязкой к **фасетам** (Manager/Object/RecordSet/…) и учётом видимости (**Экспорт** = публичный API, без **Экспорт** = приватный внутри модуля).

## Фактический прогресс (проверено по репозиторию)

Проверка выполнена по коду и тестам:

- Интеграционный тест на реальной конфигурации (если доступна `examples/conf_big`) есть: `backend/tests/config_big_modules_indexing_test.rs:1`.
- `cargo test --workspace` проходит (на момент проверки).

## Контекст (текущее состояние)

На момент написания:
- XML-метаданные конфигурации парсятся и загружаются в `TypeRepository` как `RawTypeData`, но `methods` для конфигурационных типов по-прежнему не заполняются на этом шаге (методы подтягиваются отдельной индексацией BSL-модулей): `backend/src/data/loaders/config_metadata_parser/converter.rs:94`.
- Discovery умеет находить пути к `ObjectModule.bsl / ManagerModule.bsl / RecordSetModule.bsl` для всех объектов метаданных (формы всё ещё ограничены `Document/Catalog`): `backend/src/data/loaders/config_metadata_parser/discovery.rs:440`.
- LSP `Go To Definition` использует `module_paths` только для навигации по файлам, не анализируя содержимое модулей: `backend/src/bin/lsp_server/handlers/definition.rs:47`.
- Единственный текущий анализ `*.bsl` внутри загрузки конфигурации — чтение `Form/Module.bsl` для определения контекстов выполнения модуля формы (`backend/src/data/loaders/config_metadata_parser/form_parser.rs:421`).
- Единственный источник данных о методах платформы — `syntax_helper`, а конфигурационные сигнатуры добавляются в индекс отдельным шагом (не через `SignatureDataSource`): `backend/src/data/loaders/signature_sources.rs:1`, `backend/src/bin/lsp_server/commands/configuration.rs:293`.

## Нефункциональные требования

- **Right-Sized Architecture:** не плодить новые “сервисы на каждый чих”; добавлять один понятный загрузчик модулей конфигурации.
- **Semantic IR / честная проверка:** интеграция через существующий pipeline `AST → IR → Validation/Resolver`, с проверками через тесты и grep перед отчётами.
- **Без запуска серверов:** LSP/Web серверы не трогаем; изменения — в коде загрузки/анализа.

---

## Цели и не-цели

### Цели
- Экспортные процедуры/функции из модулей конфигурации становятся **доступными как методы** соответствующих конфигурационных типов/фасетов.
- Приватные (без `Экспорт`) доступны **только внутри своего модуля** для валидации и резолвинга локальных вызовов.
- Методы из:
  - `CommonModules/*/Ext/Module.bsl`
  - `*/Ext/ObjectModule.bsl`
  - `*/Ext/ManagerModule.bsl`
  - `*/Ext/RecordSetModule.bsl`
  - (по мере необходимости) другие модульные типы
  — участвуют в индексации.
- Параметры/возвраты получают типы как минимум частично (см. ниже), с прозрачной `certainty`.

### Не-цели (на первом этапе)
- Полная семантическая модель платформы 1С (все директивы, все тонкости модульной области видимости, все особенности препроцессора).
- Полный межмодульный call-graph для всего проекта (можно идти инкрементально).

## Архитектура решения (высокоуровнево)

Добавляется отдельный слой: **Configuration BSL Module Loader**.

**Вход:**
- метаданные конфигурации (XML) + `module_paths` (если есть),
- свойства общих модулей (контексты выполнения из XML),
- доступ к файловой системе конфигурации.

**Выход:**
- “публичные” сигнатуры конфигурации (только `Экспорт`) в индекс сигнатур,
- локальная информация о приватных методах (для валидации внутри модуля),
- (опционально) `method -> code location` для будущей навигации.

Принципиально: парсинг `.bsl` использует существующий `ParserCoordinator` + `AstToIrConverter`, чтобы не плодить отдельный парсер и чтобы сохранить совместимость с flow-sensitive анализом.

## Привязка методов к фасетам и владельцам

### Модули объектов/менеджеров/наборов записей
- `ObjectModule.bsl` → фасет `Object` для типа-владельца (например `Справочники.Контрагенты` с `active_facet=Object`).
- `ManagerModule.bsl` → фасет `Manager`.
- `RecordSetModule.bsl` → фасет `RecordSet` (или принятый в проекте фасет/тип для наборов записей).

### Общие модули
- Экспортные методы доступны как:
  - методы типа `CommonModule` (singleton) **и/или**
  - глобальные функции, если `Global=true` (нужна явная политика в проекте: алиас в глобальном namespace).

---

## Видимость

- **Экспорт** → публичные сигнатуры (видимы из других модулей).
- **Без Экспорт** → приватные (видимы только внутри конкретного `*.bsl` файла модуля).

Технически: приватные не должны попадать в общий `SignatureIndex`, иначе другие модули начнут “видеть” их как существующие.

## Типизация параметров и возвращаемых значений (план)

### Возвраты (MVP)
- Для `Функция` собирать все `Возврат <expr>` и резолвить `<expr>`.
- Итоговый `return_type` = union всех типов `<expr>` (с `certainty` по правилу “монотонно ухудшается”).
- Если `Возврат` отсутствует → `Неопределено`/`Dynamic` (в зависимости от принятой модели).

### Параметры (поэтапно)
1) **Call-site inference (быстро и полезно для экспортных):**
   - собирать все вызовы экспортного метода;
   - тип аргументов на вызовах даёт наблюдения для параметров;
   - итоговый тип параметра = union наблюдений.
2) **Intra-procedural constraints (внутри функции):**
   - если параметр используется как объект с методом/свойством — ограничивать тип;
   - учитывать проверки `Если p = Неопределено` / `ТипЗнч` / `ЭтоТип` как narrowing.
3) **Итеративное уточнение по SCC графа вызовов (опционально):**
   - фикс-поинт по компонентам сильной связности, чтобы распространять типы между процедурами.

Важно: все выводы должны сохранять `certainty` и не ломать flow-sensitive модель внутри файла.

## Milestones (вертикальные срезы)

### C1: Расширить discovery модулей на все типы метаданных ✅ (сделано)
**Цель:** для всех релевантных объектов метаданных заполнять `module_paths` (не только `Document/Catalog`).

**Критерии успеха:**
- discovery находит `ObjectModule/ManagerModule/RecordSetModule` для регистров и других объектов, где эти модули есть.
- тесты на структуру путей и обнаружение.

### C1F: Парсинг форм не только для Document/Catalog ⏳ (добавлено)
**Цель:** расширить discovery/парсинг форм на другие виды метаданных (например, отчёты/обработки/… по реальной потребности), чтобы контексты и модули форм корректно учитывались не только у документов/справочников.

**Критерии успеха:**
- `discover_forms()` вызывается не только для `Document/Catalog` (или введён явный whitelist по видам метаданных).
- `discover_forms_for_object()` используется как основной API обнаружения форм (с корректным `owner_type`).
- `metadata.forms` заполняется для новых типов, где формы присутствуют.
- тесты на обнаружение форм и базовую загрузку/парсинг `Form.xml`.

### C2: Парсер BSL-модулей: извлечение процедур/функций + Export ✅ (MVP сделан)
**Цель:** получить список объявлений методов из `.bsl` модулей.

**Критерии успеха:**
- по `*.bsl` файлами модулей строится список `(name, params, is_export, directive/context, ...)`.
- корректно отсекаются приватные методы (не попадают в публичный индекс).

Примечание: MVP уже извлекает `name/params/is_export` и контекст из директив/модуля; `location` и точный признак `is_function` можно довести отдельным подэтапом, если потребуется для go-to-definition к объявлению метода.

### C3: Интеграция публичных методов в `SignatureIndex` как “Configuration” ✅ (сделано)
**Цель:** экспортные методы становятся доступны как методы типов конфигурации в hover/validation.

**Критерии успеха:**
- `hover` по `Справочники.<X>` показывает методы из `ManagerModule` только в фасете Manager, из `ObjectModule` — только в Object.
- вызов несуществующего метода даёт диагностическую ошибку, а существующего экспортного — нет.

### C4: Контексты выполнения для конфигурационных методов 🟡 (частично)
**Цель:** сохранить/использовать `ContextRequirements` при валидации.

**Критерии успеха:**
- методы из CommonModule учитывают контексты из XML + директивы на методе (если есть).
- серверные вызовы в клиентском контексте корректно диагностируются (минимально — для форм).

### C5: Типы возврата (MVP) 🟡 (частично)
**Цель:** базовый вывод return type по `Возврат`.

**Критерии успеха:**
- `SignatureIndex` для конфигурационных методов содержит return type хотя бы для простых кейсов (`Возврат 1`, `Возврат "x"`, `Возврат Новый Тип()` и т.п.).
- тесты: 2–3 функции с разными `Возврат` (один тип / разные ветки / нет возврата).

### C6: Типы параметров (MVP: call-site) ✅ (MVP)
**Цель:** вывести типы параметров экспортных методов по местам вызова.

**Критерии успеха:**
- для части экспортных методов параметры получают `type_name` по наблюдениям типов аргументов на вызовах (MVP: хотя бы литералы/Неопределено/Новый + простые локальные переменные).
- учитываются вызовы из других модулей в форме `ИмяОбщегоМодуля.Метод(...)` и `Справочники.<X>.<Метод>(...)` (минимальный межмодульный call-site).
- валидация аргументов начинает ловить очевидные ошибки по выведенным типам (с разумной `certainty`).

### C7: Полировка LSP UX (необязательное) 🟡 (частично)
**Цель:** улучшить диагностические сообщения и навигацию (например, go-to-definition к объявлению метода).

**Фактический прогресс:**
- Go To Definition поддерживает переход к объявлению экспортного метода в `*.bsl` (конфигурационные модули).
- Для глобальных функций из global common modules хранится location (и его можно использовать для перехода).
- Есть fallback на локальные объявления функций/процедур в текущем файле (включая приватные), если repo не содержит location.
- Прогон проверки: `cargo test --workspace` проходит.
