# Change: Доведение межпроцедурного вывода return‑типа до рабочего состояния (hardening)

## Зачем (проблема)
Существующая реализация межпроцедурного вывода return‑типа пользовательских экспортов частично работает, но имеет критичные разрывы, из‑за которых результат либо не применяется, либо теряется “слабость/динамика”:

- overlay для open files не покрывает все типы модулей, которые индексируются в `SignatureIndex` (сейчас фактически только common/manager);
- в persistent‑контуре (индексация конфигурации) “weak/dynamic” теряется при записи в `SignatureIndex`, поэтому call‑site типизация не может понизить `Certainty`;
- при AST fallback (когда single-pass parsing не сработал) `return_facts` отсутствуют, и межпроцедурный вывод фактически выключается на проблемных модулях.

Этот change устраняет разрывы и фиксирует единый контракт семантики: **сохранять известный union и помечать неопределённость как weak**.

## Что меняется
1) **Единый контракт return‑summary** для обоих контуров (persistent + overlay):
   - `known` (union вариантов типов) всегда сохраняется;
   - `has_dynamic` / “weak” отражает неопределённость, но не затирает известное.

2) **Persistent‑контур (индексация конфигурации)**:
   - расширяем данные, которые попадают в `SignatureIndex`, чтобы вместе со строковым `return_type` сохранялась метка weak/dynamic (через поле в `MethodSignature` или эквивалентный механизм);
   - при типизации вызовов через `SignatureIndex` учитываем метку weak и возвращаем `Certainty::InferredWeak` без потери union.

3) **Overlay для открытых файлов (analysis-v2)**:
   - owner‑mapping покрывает все модули, которые индексируются в `SignatureIndex`:
     - `CommonModule`
     - `ManagerModule`
     - `ObjectModule`
     - `RecordSetModule`
   - канонические ключи owner_type для module types:
     - ObjectModule: `СправочникОбъект.<Имя>` / `ДокументОбъект.<Имя>` / … (по `MetadataKind`)
     - RecordSetModule: `РегистрНакопленияНаборЗаписей.<Имя>` / `РегистрСведенийНаборЗаписей.<Имя>` / …
   - overlay‑фикс‑пойнт может использовать `SignatureIndex` как внешний источник summary для вызовов в неоткрытые модули (без I/O).

4) **AST fallback**:
   - в fallback‑парсинге модулей обеспечиваем хотя бы консервативные `ReturnFacts` (например, `Unknown` + `has_dynamic=true`), чтобы вывод не выключался полностью.

## Влияние и совместимость
- Затронутые подсистемы: `bsl-runtime` (индексация конфигурации), `analysis-v2` (overlay + type inference), `bsl-repository`/`shared` (контракт сигнатур).
- Может потребоваться bump версий/фингерпринтов disk cache для конфиг‑модулей при изменении сериализуемых структур.
- Изменение не должно добавлять блокирующий I/O в hot path IDE‑запросов.

## Вне скоупа (non-goals)
- Расширение overlay на модули, которые **не** индексируются в `SignatureIndex` (например, FormModule).
- Переезд существующего “двухконтурного” подхода на иной типовой pipeline; цель — довести текущий до корректного и предсказуемого поведения.
- Полный CFG‑based interprocedural inference (выше уровня summary‑подхода).
