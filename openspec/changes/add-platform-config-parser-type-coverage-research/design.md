## Context
Есть как минимум один подтверждённый симптом неполного покрытия типов: `БиблиотекаКартинок` не резолвится в пользовательском сценарии.
Судя по архитектуре v2, тип может "потеряться" в нескольких местах:
- extraction (platform/config parser),
- normalization (алиасы, канонизация имён, namespace mapping),
- ingestion в `TypeRepository`,
- facet projection (`Менеджер`/`Объект`/`Ссылка`/`Список`/`Выборка` и form-data контексты),
- `TypeMetadataLookup` и downstream resolver paths.

Сейчас нет единого end-to-end артефакта, который показывает судьбу каждого типа по стадиям pipeline.

## Goals / Non-Goals
- Goals:
  - Сделать аудит покрытия типов воспроизводимым и stage-based.
  - Получить полный список gaps с root-cause стадией и причиной.
  - Явно отразить участие фасетов в проблемах резолва.
  - Зафиксировать baseline-кейсы (включая `БиблиотекаКартинок`) как регрессионные.
- Non-Goals:
  - В рамках этого change не исправлять все найденные gaps.
  - Не менять пользовательские политики отображения типов вне необходимости для анализа.
  - Не добавлять новые языковые/грамматические возможности.

## Type Lifecycle Model
Для исследования вводится единая модель стадий:
1. `source_discovered` — тип обнаружен в первичном источнике (platform docs / config metadata).
2. `parser_extracted` — тип извлечён parser-ом в промежуточную модель.
3. `normalized` — имя и категория типа канонизированы.
4. `indexed` — тип попал в `TypeRepository`.
5. `facet_projected` — доступны ожидаемые фасетные представления (где применимо).
6. `lookup_resolvable` — тип реально резолвится через публичный lookup path.

Gap фиксируется как:
- `first_failed_stage`,
- `reason_code`,
- `details` (контекст, входные данные, affected facets).

## Facet-Aware Coverage Strategy
Аудит должен идти в двух измерениях:
- type-level: "тип вообще существует в pipeline";
- facet-level: "тип доступен в нужном фасете/контексте".

Минимальный набор фасетов для проверки:
- `Менеджер`
- `Объект`
- `Ссылка`
- `Список`
- `Выборка`

Для form-context сценариев проверяется отдельно:
- applied object facet при `FormModule.Объект`,
- form-data слой и гарантированные свойства (если применимо).

## Deliverables
- Машиночитаемый baseline-отчёт:
  - список типов;
  - статус по каждой стадии;
  - facet-level статусы;
  - gap-классификация.
- Человекочитаемый аналитический отчёт:
  - coverage метрики по источникам и стадиям;
  - топ root-cause категорий;
  - приоритезированный список follow-up изменений.

## Implementation Considerations
- Нужна стабильная нормализация идентификаторов типов, иначе сравнение source/index будет шумным.
- Для reproducibility важны:
  - фиксированный snapshot входных данных;
  - детерминированная сортировка и сериализация отчёта;
  - единые reason-коды для gap-классификации.
- Для проверки `lookup_resolvable` использовать тот же контракт, что применяет IDE path, чтобы не получить "ложно зелёный" результат.

## Risks / Trade-offs
- Риск: большой объём типов и шум в отчёте.
  - Mitigation: группировка по reason-кодам + top-N приоритезация.
- Риск: ложные gaps из-за неполной нормализации алиасов.
  - Mitigation: отдельный слой alias mapping и явный статус "alias mismatch".
- Риск: смешение parser-проблем с facet lookup-проблемами.
  - Mitigation: обязательная фиксация `first_failed_stage`.
